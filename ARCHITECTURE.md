# Архитектура baseline и контракты модулей

> Это ранний CSV-baseline. Актуальные решения backend: `docs/DECISIONS.md`.
> Контракт ядра: `docs/CORE_INTEGRATION.md`. Роль 1 — backend; роль 2 — ядро и solution.py.

Сквозной поток данных:

```text
questions.csv
    -> load_questions(path) -> list[Question]
    -> retrieve(question, knowledge, top_k) -> list[SearchResult]
    -> build_messages(question, results) -> chat messages
    -> generate_answer(question, results, settings) -> str
    -> write_submission(path, rows) -> submission.csv
```

На первом этапе реализация собрана в одном `solution.py`, чтобы релизный ZIP
оставался самодостаточным. Границы функций уже выделены и являются интерфейсами
между ролями.

## Контракт роли 2: поиск

Роль 2 заменяет внутренности `load_knowledge()` и `retrieve()`, не меняя
следующий контракт:

```python
retrieve(question: str, knowledge: Sequence[SearchResult], top_k: int = 4)
    -> list[SearchResult]
```

Каждый результат содержит `source`, `text`, `score`. Результаты отсортированы
по убыванию релевантности; при отсутствии уверенного контекста возвращается
пустой список. Поиск не генерирует ответ пользователю.

## Контракт роли 3: генерация

Роль 3 изменяет `build_messages()` и, при необходимости, параметры запроса.
На входе — нормализованный вопрос, история и результаты поиска; на выходе —
непустая строка не длиннее 10 000 символов. Генерация не читает файлы и не
знает о формате CSV.

## Контракт роли 4: валидация и упаковка

Валидатор получает пути к исходному `questions.csv` и готовому
`submission.csv`. Он проверяет схему `id,answer`, соответствие и уникальность
ID, непустые ответы и лимит длины. Упаковщик кладёт `solution.py` и
`requirements.txt` в корень ZIP.

## Инварианты интеграции

- ID всегда трактуется как строка и не преобразуется в число.
- Секреты читаются только из окружения и не выводятся в лог.
- Ошибка одного LLM-запроса не должна оставлять пустой ответ.
- Источники контекста передаются в промпт, но внутренние пути не обязательны в
  финальном ответе.
- Любая новая зависимость фиксируется точной версией в `requirements.txt`.
