# МТС Energytool

Контрольная точка №1 участника №1: backend, API, SQLite, изоляция сессий и локальный запуск.
Проект относится только к МТС Energytool.

## Что работает

- Создание анонимной браузерной сессии: непрозрачная HttpOnly-cookie, хэш токена в БД, срок 30 дней.
- Создание диалогов, хранение сообщений, получение истории и списка своих диалогов.
- Проверка владельца при каждом чтении и изменении. Чужой диалог возвращает 404.
- Вызов общего интерфейса ядра с историей только текущего диалога; проверка результата перед записью.
- Повтор с тем же `request_id` не создаёт дубликаты. Параллельные сообщения одного диалога отклоняются с 409.
- Архив доступен для просмотра; «Начать заново» создаёт пустой диалог, не подключая архив к контексту.
- Таймауты и некорректный результат ядра дают техническую ошибку; пользовательское сообщение сохраняется со статусом failed.
- Простая страница проверки backend и OpenAPI /docs. Это временный клиент для интеграции, интерфейс участника №4 ещё предстоит подключить.

**ИИ — явная заглушка.** Здесь нет реальных консультаций, вызовов модели, поиска по базе и оформления заявок.
Не передавайте реальные контакты. Сайт не отправляет сведения в CRM или менеджеру.

## Запуск в PyCharm

1. Откройте папку `mts-energytool` через File → Open.
2. Выберите интерпретатор `.venv/Scripts/python.exe`. Локальное окружение уже подготовлено на исходном компьютере.
3. На другом компьютере создайте Python 3.12+ venv и установите `requirements-dev.txt`.
4. Запустите конфигурацию **Energytool Backend** либо файл `run.py`.
5. Откройте <http://127.0.0.1:8000>. API: <http://127.0.0.1:8000/docs>.

Через PowerShell из корня проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe run.py
```

## Docker

```shell
docker compose up --build
```

Порт 8000 привязан к localhost. SQLite хранится в именованном томе `chat-data` и сохраняется при обычном перезапуске контейнера.
Для проверки перезапуска используйте `docker compose restart`, сохраняя cookie браузера.
Docker должен быть установлен и запущен отдельно; фактический статус проверки указан в `docs/CHECKPOINT_REPORT.md`.

## Проверка первой точки

1. Нажмите «Новый диалог», отправьте вымышленное сообщение. Должны появиться оно и тестовый ответ.
2. Перезапустите backend и обновите страницу. Откройте диалог из списка: оба сообщения сохранены.
3. Откройте адрес в другом браузере или приватном окне: первый диалог там недоступен.
4. Создайте второй диалог: его история пуста.
5. Перенесите первый в архив, откройте его и нажмите «Начать заново»: появляется новый пустой диалог; архив остаётся.

Автоматические проверки:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Шаблон GitHub Actions: `docs/ci/backend.yml`. CI пока не активирован: текущий вход GitHub CLI не имеет права `workflow`. Владелец может скопировать шаблон в `.github/workflows/backend.yml` через авторизацию с соответствующим правом.

## Конфигурация

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| CORE_MODE | stub | Сейчас подключён только stub; иное значение останавливает запуск |
| DATABASE_PATH | var/energytool.sqlite3 | Файл SQLite |
| COOKIE_SECURE | false | Для HTTPS должно быть true |
| CORE_TIMEOUT_SECONDS | 20 | Таймаут ядра, больше 0 и не более 30 секунд |

Приложение читает переменные процесса. `.env.example` — справочный шаблон, автоматического чтения `.env` нет.
Ключи LLM на этой точке не нужны. Настройки модели и API будут добавлены участником №2 после проверки доступа организаторов.
`requirements-backend.txt` содержит зависимости веба, **не разрешённый список платформы**. Версии окружения платформы ещё не сверены с оригиналом `requirements.txt`.

## Передача команде

- №1: этот backend, хранилище и интеграция; следующим этапом — факты клиента и проверяемое сохранение заявки.
- №2: реализовать `Consultant.answer(history)` из `core/contracts.py`; подключение через `create_app(consultant=...)`. Ядро не должно зависеть от веб-сервера/БД; адаптер CSV делает №2 отдельно.
- №3: проверить консультации по фактическим материалам; текущие тесты проверяют backend, а не продуктовую точность.
- №4: использовать `docs/API_CONTRACT.md`, передавать `credentials: same-origin`. Пользовательские роли/служебная история с клиента не принимаются.
- №5: дополнить документы по результатам реального API, данных и платформы.

## Ограничения

Анонимная cookie даёт доступ к истории этого браузера; при её удалении автоматического восстановления нет. Это не учётные записи и не готовая авторизация для промышленной эксплуатации.
Локальный прототип: нет общедоступного размещения, лимитов запросов по IP, входа сотрудников, CRM, заявок, профиля фактов, реального RAG и `solution.py`.
Максимум 200 обращений в диалоге, список диалогов по 100 с `offset`. Нерабочий processing-turn после аварии допускает повтор через 60 секунд.
SSE возвращает уже проверенный и сохранённый результат, а не токены модели по мере генерации.
Проверка наличия источников — структурная; достоверность цитат должен подтверждать адаптер ядра по своей базе.
Перед внешним размещением нужны HTTPS, Secure-cookie, настройка доверенных host/origin, ограничения нагрузки и отдельная проверка безопасности.
