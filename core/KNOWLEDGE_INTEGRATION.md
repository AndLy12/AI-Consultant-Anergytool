# Подключение настоящей базы к ядру

13 ноября 2026, ветка `codex/core-knowledge-base`, основа `origin/core:8f78871`.
Область работы: ядро Данька, `solution.py` и инструменты базы Ани. Backend,
миграции, API-контракт, frontend, Docker и веб-зависимости не изменены.

## Полученные материалы

Исходники получены из [папки организаторов](https://drive.google.com/drive/folders/1EKFXt51aswP5IEAAcIXAcNl_geX1sdW5).
Изучены PDF кейса, [технический регламент](https://docs.google.com/document/d/1wZsqH4xXZXwjiAJCtFQGjTaLxEU3D_tMCSw0yXcbQ0U/edit),
оригинальные `requirements.txt`, `sample_submission.zip`, `demo_questions.csv`
и `demo_output.csv`. Доступ к платформенной модели передаётся окружением
автоматически; собственный ключ для платформенного запуска не нужен.

Локально в игнорируемой `knowledge-base-work/data/` находятся архив, 19
исходных Markdown-документов, 148 разделов подготовки Ани и официальные примеры.
Подготовка воспроизведена инструментом Ани. Исходные байты сохраняются; два
структурных замечания источников остаются в локальном реестре, не исправляются
подменой фактов. Документы, вопросы, эталоны и производные данные не коммитятся.

Индекс строится из исходного архива/каталога документов. `kb-artifacts` —
реестр для сверки, а не готовый индекс ядра. Эталонные demo-ответы не
индексируются и не передаются модели как факты базы.

## Изменения ядра

- Исключены 27 фрагментов с одним оформлением: осталось 477 содержательных
  фрагментов. Текст и ID сохранённых фрагментов совпадают с прежней версией.
- Иерархия Markdown позволяет добавлять весь родительский раздел вместе с
  вложенными пунктами. Ограничения и границы применения того же документа
  также участвуют в расширении контекста. Дополнительный раздел включается
  целиком, если помещается; бюджет 14 000 символов не превышается.
- Улучшено совпадение русских словоформ, включая короткие существительные
  и окончания прилагательных; убраны частые служебные слова запроса.
  Отрицания не удаляются. Это эвристический BM25, не семантическая модель.
- Источники показывают заголовок документа вместо технического имени файла.
- `CHUNKER=common` совместим с текущим смысловым разбиением `sections`.
  Произвольные неизвестные значения по-прежнему отклоняются.
- Все семь зависимостей платформенного ядра и их версии найдены в
  оригинальном разрешённом списке. Зависимости веба не менялись.
- Проверки подготовки Ани работают на Windows с явным UTF-8; опасные имена
  ZIP проверяются по исходному `orig_filename`, до нормализации Windows.

## Как проверить без backend и без API

Из корня проекта с установленными зависимостями ядра:

```powershell
.\.venv\Scripts\python.exe scripts/check_core_knowledge.py --data-dir knowledge-base-work/data --questions knowledge-base-work/data/demo_questions.csv
.\.venv\Scripts\python.exe -m pytest tests/core -q
.\.venv\Scripts\python.exe scripts/build_core_submission.py --output work/core-knowledge-submission.zip
```

Проверки инструментов Ани запускаются из `knowledge-base-work`:

```powershell
..\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Локально на Python 3.12.14 прошли 81 тест проекта (из них 52 в `tests/core`)
и отдельно все 20 тестов инструментов Ани. Шаблон `core/ci/core.yml` подготовлен для проверки ядра без веб-зависимостей
и инструментов подготовки на Linux и Windows. Он не активирован: GitHub
отклонил отправку нового workflow из-за отсутствия права `workflow` у текущего
OAuth-подключения. Локальные результаты выше не являются результатами GitHub CI.

`check_core_knowledge.py` использует тот же поиск, ограничение истории и
контекст, что и `respond`. Подробности сохраняет в `work/`, в консоль выводит
только агрегаты. Результат: 19 документов, 477 фрагментов, ни одного фрагмента
только с оформлением; все 18 официальных вопросов разобраны, пять содержат
историю диалога, для всех 18 есть поисковый контекст. Это не Recall и не
подтверждение правильности выбранного основания.

Проверен сквозной запуск `solution.py` на этих 18 строках из исходников и из
плоского ZIP в отдельном пустом каталоге. Обе проверки использовали локальный
HTTP-мок вместо модели: 18/18 ID сохранены, технических ошибок нет, история
всех 36 запросов передана ровно в соответствии с CSV. Ответы мока не являются
консультациями и не оценивают качество LLM.

## Реальный вызов

Локально задаются переменные без записи секретов в Git:

```powershell
$env:DATA_DIR = (Resolve-Path knowledge-base-work/data).Path
$env:CORE_DEMO = 'false'
# Адрес, ключ и имя локальной модели задаются в окружении отдельно.
.\.venv\Scripts\python.exe solution.py --questions knowledge-base-work/data/demo_questions.csv --output work/real-submission.csv
```

На платформе достаточно запустить `solution.py`: `DATA_DIR/questions.csv`,
база и доступ к модели передаются организаторами. Архив поставки содержит
только 13 корневых файлов кода и зависимостей, без закрытой базы и примеров.
