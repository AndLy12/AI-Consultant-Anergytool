# Ядро МТС Energytool

Ветка `core` продолжает актуальный командный backend. Это BM25 baseline с проверкой цитат и явной демонстрацией, а не подтверждённый результат на базе организаторов.

## Что реализовано

- Общая фабрика `consultant_core.create_core()` и синхронный `respond(CoreRequest) -> CoreResponse`, совместимые с текущим backend.
- Чтение TXT, MD, CSV, JSON, DOCX и текстовых PDF; ZIP читается в памяти с проверкой путей, символьных ссылок, дублей и размеров.
- Смысловые фрагменты с устойчивыми ID, разделами, страницами и смещениями внутри извлечённого блока. В DOCX сохраняется порядок абзацев/таблиц; заголовки колонок повторяются у строк таблицы.
- BM25Plus, одинаковая нормализация запроса и документов, история последних пользовательских реплик, добавление соседних пунктов в пределах бюджета.
- Qwen-совместимый `chat/completions`, проверяемая JSON-структура без обязательного tool calling или принудительного JSON-режима.
- Точный поиск цитаты в использованном фрагменте; названия и координаты берутся из индекса. Нет свободного пересказа неподтверждённых продуктовых фактов.
- Независимость диалогов, ограничение истории, параллельности, времени и сетевых повторов. Ключ не попадает в промпт, ответ или диагностику.
- Общий `solution.py`, атомарный CSV, сохранение всех ID даже при технических сбоях, агрегированный отчёт без вопросов и ответов.
- Сборка плоского ZIP без backend, БД, исходных документов, индексов, `.env`, фронтенда и вложенных пакетов.

## Быстрая демонстрация без API и настоящих документов

Нужен Python 3.12+. Виртуальное окружение `.venv` в рабочей папке ветки уже подготовлено на исходном компьютере.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
$env:CORE_DEMO = 'true'
.\.venv\Scripts\python.exe solution.py --questions examples/core-demo/questions.csv --output work/demo-submission.csv
.\.venv\Scripts\python.exe solution.py --questions examples/core-demo/questions.csv --output work/demo-submission.csv --validate-only
```

Модель в этом режиме не вызывается. Вымышленный «Учебный стенд Альфа» не описывает продукт Energytool. Ответы и предупреждения явно обозначают демонстрацию. Набор не является demo-файлами организаторов и не измеряет качество настоящей модели.

## Подключение к вебу

Для веба используется отдельный файл установки, чтобы не столкнуть Pydantic 2.14.3 из веб-lock и кандидат 2.14.2 из платформенной инструкции:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-core-web.txt
$env:CORE_DEMO = 'true'
$env:CORE_MODE = 'real'
$env:CORE_MODULE = 'consultant_core'
.\.venv\Scripts\python.exe -m backend.check_core --message 'Как экспортировать отчёт стенда Альфа?'
.\.venv\Scripts\python.exe run.py
```

В этой комбинации `CORE_MODE=real` означает загрузку фабрики backend, а `CORE_DEMO=true` — вымышленную базу и заглушку модели внутри неё. Слово `real` в диагностике backend не подтверждает реальный API. Проверяйте предупреждения ответа и настройку `CORE_DEMO`.

Аккаунт, согласие и запись заявки остаются в backend. История приходит в запросе и не хранится ядром между вызовами. `summary_draft` — только проверяемые выдержки из пользовательских сообщений по его явной просьбе; это не приказ записать заявку. Готовность и актуальность карточки подтверждает пользователь через backend.

## Обычный режим после получения базы и API

1. Установить `CORE_DEMO=false`.
2. В `DATA_DIR` разместить закрытый `knowledge-base.zip` либо каталог `knowledge-base`. `questions.csv` лежит рядом, но в индекс не попадает.
3. При другом расположении явно задать `CORE_KB_PATH`. Каталог должен содержать только материалы базы; вопросы и образцы ответов в нём размещать нельзя.
4. Настроить URL, ключ и модель через окружение. Значения не коммитить.
5. Проверить загрузку: `python -m backend.check_core`.
6. На согласованном тестовом вопросе проверить реальный вызов, источники, время и ограничения ответа.
7. Прогнать CSV и независимый размеченный набор. Только затем оценивать качество и улучшать поиск.

Ключ читается из `LLM_API_KEY` или `OPENAI_API_KEY`; URL — `LLM_BASE_URL` или `OPENAI_BASE_URL`; модель — `LLM_MODEL`, `OPENAI_MODEL` или `GEN_MODEL`. Никакое имя Qwen не зашито в код. Для разработки и платформы используются разные значения окружения, без автоматического переключения при ошибке.

Маршрут — `chat/completions` относительно точного переданного base URL. `/v1` самовольно не добавляется. Редиректы с Bearer-ключом не выполняются. 401/403 не повторяются; 429/5xx и сетевые ошибки повторяются ограниченно.

## Настройки

Справочный шаблон: [`.env.example`](.env.example). Ядро само не читает этот файл; `run.py` backend может читать корневой `.env` по своим правилам.

| Переменная | По умолчанию | Значение |
|---|---|---|
| CORE_DEMO | false | Только явное true включает вымышленные материалы и заглушку |
| DATA_DIR | data | Корень платформенных входов |
| CORE_KB_PATH | не задан | Явный ZIP/каталог/файл базы, если нужен |
| TOP_K | 5 | Первые кандидаты BM25, 1–20 |
| CHUNKER | sections | Поддерживается только текущее смысловое разбиение |
| CORE_CHUNK_CHARS | 1800 | Размер фрагмента в символах, не токенах |
| CORE_CONTEXT_CHARS | 14000 | Бюджет текстов источников |
| CORE_HISTORY_CHARS | 16000 | Последние целые реплики истории |
| TEMPERATURE | 0.1 | Настройка генерации, не гарантия истинности |
| MAX_TOKENS | 1200 | Лимит генерации |
| CORE_TIMEOUT_SECONDS | 60 | Время respond, 1–120 секунд |
| LLM_TIMEOUT_SECONDS | 15 | Таймаут сетевой операции |
| LLM_MAX_RETRIES | 2 | Дополнительные попытки, 0–3 |
| MAX_WORKERS | 4 | Параллельность CSV и запросов модели, 1–16 |
| SUBMISSION_TIMEOUT_SECONDS | 1140 | Общий бюджет CSV, максимум 19 минут |

`EMB_MODEL`, `RERANKER_MODEL` и `RERANKER_TOP_N` не включают скрытые возможности: эмбеддинги и реранкер пока не реализованы. Их адреса и схемы API неизвестны, качество сравнивать пока не на чем.

## Что получает модель и как проверяется ответ

Служебная инструкция версионируется в `prompts.py`. В пользовательском JSON передаются текущая реплика, ограниченная история и найденные документы. Текст с `system:` не становится служебной ролью. Действующий серверный ключ вырезается даже при его случайном появлении в документе.

Модель возвращает статус, до трёх пар `chunk_id + quote`, уточнение при необходимости, недостающие сведения и необязательный черновик резюме. Поле с произвольным готовым ответом не принимается. Код проверяет ID, точную непрерывную цитату и схему, затем собирает ответ с источниками.

Это защищает от выдуманных цитат и неподтверждённого свободного пересказа. **Это не доказывает, что выбран правильный документ, сохранены все условия или дан полный полезный ответ.** Такие ошибки должны выявляться человеком и размеченным набором. Инструкция модели и цитирование не гарантируют абсолютную защиту от prompt injection.

Целевая краткость задана инструкцией; до измерений на реальных материалах используются жёсткие пределы цитат/ответа, а не обещание 150 слов для каждого случая. Слишком длинный или повреждённый результат отклоняется, смысловой ответ молча не обрезается.

## CSV и упаковка

Вход — UTF-8, ровно `id,question`; ID не перенумеровываются. История внутри `question` поддерживает JSON-массив user/assistant или строки `Пользователь:`/`Ассистент:`. Незнакомый формат не угадывается и обрабатывается как одно пользовательское сообщение; реальные demo-файлы потребуют сверки парсера. После любого преобразования системных ролей из строки не возникает.

Выход — UTF-8, ровно `id,answer`. Перед загрузкой ядра создаются технические запасные ответы для всех ID; после завершённых обращений CSV атомарно обновляется. Сбои не маскируются отсутствием фактов. Соседний `.report.json` содержит только количество строк, ошибки и время.

```powershell
.\.venv\Scripts\python.exe scripts/build_core_submission.py --output work/core-submission.zip
```

Сборщик копирует только оговорённые модули и преобразует импорты `core.*` в корневые `energytool_*`. Канонический код остаётся в `core/`, вручную две версии не поддерживаются. ZIP — кандидат, а не подтверждённый платформой сабмит. Список и версии зависимостей взяты из приложенной инструкции, оригинальный whitelist пока не получен.

## Проверки и ограничения

Тесты: `python -m pytest -q`. Они используют только синтетические документы, HTTP-моки и отдельные временные БД. Есть проверка запуска плоского ZIP в пустой папке без `core/`, backend и веб-БД.

Полный актуальный результат: [REPORT.md](REPORT.md). Список задач: [PLAN.md](PLAN.md).

Ограничения: нет настоящей базы/API, оценки платформы, официальных demo и подтверждённого Python платформы; нет OCR, нормализации сложных PDF-таблиц и Excel/HTML; ограниченные большие файлы отклоняются; нет векторного поиска и реранкера. Пустые/неподдерживаемые материалы не игнорируются молча. Необходимые доработки определяются после изучения фактического архива.

Ограничение истории может убрать ранние сведения; это отмечается предупреждением. Сводка фактов и исправления в долгих разговорах требуют дополнительных сценариев по реальной модели. Индекс строится один раз; время его подготовки и полный лимит 20 минут ещё предстоит измерить на настоящих данных. Python-парсер или синхронное индексирование нельзя жёстко прервать одним HTTP-таймаутом.

## Для backend-разработчика

Контракт `core_contract.py` не менялся. Каталоги backend и миграции не переписывались. Изменение Dockerfile касается установки дополнительных RAG-зависимостей через `requirements-core-web.txt`; образ не содержит закрытую базу. Для обычного режима нужно отдельно подключить закрытый read-only каталог и `DATA_DIR`. Текущий compose без такого монтирования подходит для demo-режима.

Демонстрация для Docker: добавить `CORE_DEMO=true`, `CORE_MODE=real` и остальные backend-параметры в локальный `.env`, затем использовать существующий compose. Docker-сборка в этой работе не подтверждена: Docker отсутствует в окружении. Перенос ветки `core` в `main` выполняется отдельно после проверки командой.
