# Ядро МТС Energytool

Каноническое ядро находится в `core/`. Ветка `codex/core-knowledge-base` подключает настоящую базу организаторов и инструменты Ани, не меняя backend и интерфейс. Поиск проверен на исходных документах, официальном demo CSV и новой разметке Ани. Для проверки готовых ответов на локальной модели см. [методику сравнения](../eval/README.md). Подключение: [KNOWLEDGE_INTEGRATION.md](KNOWLEDGE_INTEGRATION.md); актуальные измерения поиска: [ANNA_REVIEW_UPDATE.md](ANNA_REVIEW_UPDATE.md).

## Что реализовано

- Общая фабрика `consultant_core.create_core()` и синхронный `respond(CoreRequest) -> CoreResponse`, совместимые с текущим backend.
- Чтение TXT, MD, CSV, JSON, DOCX и текстовых PDF; ZIP читается в памяти с проверкой путей, символьных ссылок, дублей и размеров.
- Смысловые фрагменты с устойчивыми ID, разделами, страницами и смещениями внутри извлечённого блока. В DOCX сохраняется порядок абзацев/таблиц; заголовки колонок повторяются у строк таблицы.
- BM25Plus ранжирует смысловые разделы, затем выбирает исходный фрагмент внутри каждого. Нормализация словоформ и единиц одинакова для запроса и документов; учитываются последние пользовательские реплики. Оформление без данных исключается; контекст дополняется родительским разделом и ограничениями того же документа в пределах бюджета.
- Qwen-совместимый `chat/completions`, проверяемая JSON-структура с согласованием json_schema, json_object и обычного ответа при отказе провайдера от расширений.
- Проверка выбранных источников. Названия, исходный текст и координаты берутся из индекса. Смысловую точность пересказа оценивают отдельно.
- Независимость диалогов, ограничение истории, параллельности, времени и сетевых повторов. Ключ не попадает в промпт, ответ или диагностику.
- Общий `solution.py`, атомарный CSV, сохранение всех ID даже при технических сбоях, агрегированный отчёт без вопросов и ответов.
- Сборка плоского ZIP без backend, БД, исходных документов, индексов, `.env`, фронтенда и вложенных пакетов.

## Быстрая демонстрация без API и настоящих документов

Нужен Python 3.12+. Виртуальное окружение `.venv` в рабочей папке ветки уже подготовлено на исходном компьютере.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
$env:CORE_DEMO = 'true'
.\.venv\Scripts\python.exe solution.py --questions examples/core-demo/questions.csv --output work/demo-submission.csv
.\.venv\Scripts\python.exe solution.py --questions examples/core-demo/questions.csv --output work/demo-submission.csv --validate-only
```

Модель в этом режиме не вызывается. Вымышленный «Учебный стенд Альфа» не описывает продукт Energytool. Ответы и предупреждения явно обозначают демонстрацию. Набор не является demo-файлами организаторов и не измеряет качество настоящей модели.

## Подключение к вебу

Для веба используется отдельный файл установки, чтобы не столкнуть Pydantic 2.14.3 из веб-lock и кандидат 2.14.2 из платформенной инструкции:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-core-web.txt
$env:CORE_DEMO = 'true'
$env:CORE_MODE = 'real'
$env:CORE_MODULE = 'consultant_core'
.\.venv\Scripts\python.exe -m backend.check_core --message 'Как экспортировать отчёт стенда Альфа?'
.\.venv\Scripts\python.exe run.py
```

В этой комбинации `CORE_MODE=real` означает загрузку фабрики backend, а `CORE_DEMO=true` — вымышленную базу и заглушку модели внутри неё. Слово `real` в диагностике backend не подтверждает реальный API. Проверяйте предупреждения ответа и настройку `CORE_DEMO`.

Аккаунт, согласие и запись заявки остаются в backend. История приходит в запросе и не хранится ядром между вызовами. `summary_draft` — только проверяемые выдержки из пользовательских сообщений по его явной просьбе; это не приказ записать заявку. Готовность и актуальность карточки подтверждает пользователь через backend.

## Настоящая база и обычный режим

В этом checkout исходный архив уже лежит локально в `knowledge-base-work/data/knowledge-base.zip`, подготовлены 19 документов. Проверка без API и без backend:

```powershell
.\.venv\Scripts\python.exe scripts/check_core_knowledge.py --data-dir knowledge-base-work/data --questions knowledge-base-work/data/demo_questions.csv
```

Для вызова ядра или `solution.py` задайте `DATA_DIR` абсолютным путём к этой папке и `CORE_DEMO=false`. На платформе `DATA_DIR`, адрес, ключ и модель передаются окружением автоматически; локально доступ к настоящей модели настраивается отдельно. Служебные артефакты и demo-ответы в индекс не попадают.

1. Установить `CORE_DEMO=false`.
2. В `DATA_DIR` разместить закрытый `knowledge-base.zip` либо каталог `knowledge-base`. `questions.csv` лежит рядом, но в индекс не попадает. CSV-адаптер также поддерживает `train.csv`, архивы `knowledge_base.zip` и `kb.zip`, а при отсутствии входов в `DATA_DIR` проверяет рабочий каталог, как официальный пример организаторов. Явные `--questions` и `CORE_KB_PATH` имеют приоритет.
3. При другом расположении явно задать `CORE_KB_PATH`. Каталог должен содержать только материалы базы; вопросы и образцы ответов в нём размещать нельзя.
4. Настроить URL, ключ и модель через окружение. Значения не коммитить.
5. Проверить загрузку: `python -m backend.check_core`.
6. На согласованном тестовом вопросе проверить реальный вызов, источники, время и ограничения ответа.
7. Прогнать CSV и независимый размеченный набор. Только затем оценивать качество и улучшать поиск.

Ключ читается из `LLM_API_KEY` или `OPENAI_API_KEY`; URL — `LLM_BASE_URL`, `OPENAI_BASE_URL` или `BASE_URL`; модель — `LLM_MODEL`, `OPENAI_MODEL` или `GEN_MODEL`. Никакое имя Qwen не зашито в код. Для разработки и платформы используются разные значения окружения, без автоматического переключения при ошибке.

Маршрут — `chat/completions` относительно точного переданного base URL. `/v1` самовольно не добавляется. Редиректы с Bearer-ключом не выполняются. 401/403 не повторяются; 429/5xx и сетевые ошибки повторяются ограниченно.

## Настройки

Справочный шаблон: [`.env.example`](.env.example). Ядро само не читает этот файл; `run.py` backend может читать корневой `.env` по своим правилам.

| Переменная | По умолчанию | Значение |
|---|---|---|
| CORE_DEMO | false | Только явное true включает вымышленные материалы и заглушку |
| DATA_DIR | data | Корень платформенных входов |
| CORE_KB_PATH | не задан | Явный ZIP/каталог/файл базы, если нужен |
| TOP_K | 5 | Число найденных смысловых разделов BM25, 1–30 |
| CHUNKER | sections | sections и совместимое имя common используют текущее смысловое разбиение |
| CORE_CHUNK_CHARS | 1800 | Размер фрагмента в символах, не токенах |
| CORE_CONTEXT_CHARS | 14000 | Бюджет текстов источников |
| CORE_HISTORY_CHARS | 16000 | Последние целые реплики истории |
| TEMPERATURE | 0.1 | Настройка генерации, не гарантия истинности |
| MAX_TOKENS | 1200 | Лимит генерации |
| CORE_REVIEW_ANSWERS | true | Дополнительная проверка консультации по тем же источникам |
| CORE_TIMEOUT_SECONDS | 100 | Время respond, 1–120 секунд |
| LLM_TIMEOUT_SECONDS | 85 | Таймаут сетевой операции |
| LLM_MAX_RETRIES | 2 | Дополнительные попытки, 0–3 |
| MAX_WORKERS | 4 | Параллельность CSV и запросов модели, 1–16 |
| SUBMISSION_TIMEOUT_SECONDS | 1140 | Общий бюджет CSV, максимум 19 минут |

При заданном `RERANKER_MODEL` ядро отправляет кандидатов BM25 и абзацы двух ведущих документов на платформенный `/rerank`. В контекст проходят до `TOP_K` результатов с исходными ID. Сбой или некорректный ответ реранкера сохраняет порядок BM25. На этот этап отводится до пятой части оставшегося времени запроса, максимум пять секунд. Цитаты с другими пробельными символами сверяются по последовательности слов и знаков, пользователю возвращается исходная подстрока.

## Что получает модель и как проверяется ответ

Служебная инструкция версионируется в `prompts.py`. В пользовательском JSON передаются текущая реплика, ограниченная история и найденные документы. Текст с `system:` не становится служебной ролью. Действующий серверный ключ вырезается даже при его случайном появлении в документе.

Модель возвращает статус, связный `answer` для `answered`, до трёх ID фрагментов из текущего запроса, уточнение при необходимости, недостающие сведения и необязательный черновик резюме. Код проверяет ID, подставляет фрагмент из индекса и проверяет схему. В старом формате с явной цитатой проверяет также её точность. Ответы старых клиентов без `answer` по-прежнему собираются из цитат. Завершённый блок `<think>` и внешняя Markdown-обёртка JSON удаляются до проверки. При ошибке структуры или оснований допускается одна коррекция в пределах прежнего дедлайна и слота параллельности.

Проверка отклоняет выдуманные цитаты. Совпадение цитат само по себе не подтверждает все утверждения в связном ответе, правильность выбора документа и полноту ограничений. Эти свойства требуют оценки на размеченном наборе. Инструкция модели и цитирование не гарантируют абсолютную защиту от prompt injection.

Целевая краткость задана инструкцией; до измерений на реальных материалах используются жёсткие пределы цитат/ответа, а не обещание 150 слов для каждого случая. Слишком длинный или повреждённый результат отклоняется, смысловой ответ молча не обрезается.

## CSV и упаковка

Вход — UTF-8, ровно `id,question`; ID не перенумеровываются. История внутри `question` поддерживает JSON-массив user/assistant или строки `Пользователь:`/`Ассистент:`. Формат подтверждён на 18 официальных demo-строках, включая пять диалогов. Незнакомый формат остаётся одним пользовательским сообщением. После преобразования системных ролей из строки не возникает.

Выход — UTF-8, ровно `id,answer`. Перед загрузкой ядра создаются технические запасные ответы для всех ID; после завершённых обращений CSV атомарно обновляется. Сбои не маскируются отсутствием фактов. Соседний `.report.json` и событие `submission_report` в stdout содержат агрегаты, признак инициализации и категории ошибок без текстов вопросов, ответов и ключей.

```powershell
.\.venv\Scripts\python.exe scripts/build_core_submission.py --output work/core-submission.zip
```

Сборщик копирует только оговорённые модули и преобразует импорты `core.*` в корневые `energytool_*`. Канонический код остаётся в `core/`, вручную две версии не поддерживаются. Все семь зависимостей и их версии сверены с оригинальным requirements организаторов. ZIP — кандидат, его приёмка платформой ещё не подтверждена.

## Проверки и ограничения

Тесты: `python -m pytest -q`. Они используют только синтетические документы, HTTP-моки и отдельные временные БД. Есть проверка запуска плоского ZIP в пустой папке без `core/`, backend и веб-БД.

Результат проверки 6v: [QUALITY_6v_2026-11-14.md](QUALITY_6v_2026-11-14.md). Предыдущий отчёт: [REPORT.md](REPORT.md). Список задач: [PLAN.md](PLAN.md).

Ограничения: локальная модель и закрытая модель площадки могут различаться; нет OCR, нормализации сложных PDF-таблиц и Excel/HTML; большие файлы отклоняются; векторный поиск не подключён; реранкер доступен через API площадки. Настоящая база, demo, пример сабмита и регламент получены и проверены. Пустые/неподдерживаемые материалы не игнорируются молча.

Ограничение истории может убрать ранние сведения; это отмечается предупреждением. Сводка фактов и исправления в долгих разговорах требуют сценариев по реальной модели. Индекс строится один раз; время реальной генерации измеряется в отчёте каждого CSV. Соблюдение лимита 20 минут на закрытом наборе зависит от его размера и скорости API площадки. Python-парсер или синхронное индексирование нельзя жёстко прервать одним HTTP-таймаутом. При малом бюджете контекста могут не поместиться все условия; наличие точной цитаты не доказывает полноту консультации.

## Для backend-разработчика

Контракт `core_contract.py` не менялся. Каталоги backend и миграции не переписывались. Изменение Dockerfile касается установки дополнительных RAG-зависимостей через `requirements-core-web.txt`; образ не содержит закрытую базу. Для обычного режима нужно отдельно подключить закрытый read-only каталог и `DATA_DIR`. Текущий compose без такого монтирования подходит для demo-режима.

Демонстрация для Docker: добавить `CORE_DEMO=true`, `CORE_MODE=real` и остальные backend-параметры в локальный `.env`, затем использовать существующий compose. Docker-сборка в этой работе не подтверждена: Docker отсутствует в окружении. Перенос ветки `core` в `main` выполняется отдельно после проверки командой.


## Проверка качества перед передачей команде

Для обычного режима включена дополнительная проверка ответа по той же истории и документам.
Она сначала перечисляет замечания, отдельно выбирает полезный следующий вопрос и возвращает исправленную консультацию. Вопрос добавляется к ответу с сохранением публичного контракта.
Проверка использует не более половины оставшегося бюджета respond и не более 35 секунд.
Если дополнительный вызов не завершился, ядро возвращает уже проверенный по структуре и
источникам первоначальный ответ с предупреждением. Это сохраняет результат при сетевом сбое.
Режим можно отключить через CORE_REVIEW_ANSWERS=false для измеримого сравнения скорости.

Источник с D1, D2 и далее действует только в текущем запросе. Сервер возвращает исходные
ID и текст из индекса. При явной просьбе о резюме повреждённый черновик восстанавливается
из целых сообщений пользователя в пределах 3000 символов. В длинной истории могут войти
только последние помещающиеся реплики. Подтверждение заявки выполняется через backend.

Команды содержательной проверки, локального судьи и журнала роли 3 приведены в
[eval/README.md](../eval/README.md).


При явной просьбе о резюме черновик также показывается в answer, чтобы не теряться
в конкурсном CSV. Уже написанное в ответе резюме не дублируется сырыми выдержками
с прежними параметрами. Отдельное поле summary_draft сохраняется для карточки backend.
Пользователь подтверждает актуальность и готовность заявки отдельно.

Конкретный список подготовки, явно указанная ценовая категория и оговорка профиля
сохраняются перед результатами реранкера. Для отдельного вопроса о вечерней или ночной
нагрузке контекст ограничивается исходными условиями профиля и резерва. Составные
вопросы о цене, диапазоне мощности и размещении сохраняют общий продуктовый контекст.
Ошибка переполнения контекста не считается отказом API от опций генерации.


В 6v добавлена узкая проверка прилагательного «бесплатный» перед обследованием,
аудитом и монтажом. Без подтверждения в выбранных источниках прилагательное
удаляется с предупреждением. Это не означает платность работ и не заменяет
содержательную проверку всей консультации. Пользовательские сведения в резюме
не переписываются этой проверкой.


Условие верификации перед коммерческим учётом для распознанных показаний при пропуске
моделью добавляется из точного фрагмента того же документа в текущем контексте.
Фрагмент возвращается также в sources. Другой продукт источником ограничения не служит.
