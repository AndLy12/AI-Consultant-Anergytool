# Результат реализации ядра

Исторический отчёт первой версии от 12 ноября. Результат подключения настоящей
базы 13 ноября и текущие ограничения: [KNOWLEDGE_INTEGRATION.md](KNOWLEDGE_INTEGRATION.md).

Дата: 12 ноября 2026 года. Рабочая ветка: `core`. Основа: командный `main`, коммит `eec073b`.

## Основания

Повторно прочитаны инструкция МТС Energytool, DECISIONS.md, AGENTS.md, текущий core_contract.py и docs/CORE_INTEGRATION.md. Учтены прямые уточнения владельца: команда из четырёх человек, backend делает другой участник, владелец занимается ядром; настоящих данных и API пока нет, разрешён явный демонстрационный режим.

Документы ПСБ не использованы как требования. Backend, миграции и общий контракт не переписаны. В main эта ветка не сливается автоматически.

## Сделано

1. Составлен [план задач C1–C9](PLAN.md).
2. Добавлена фабрика consultant_core.create_core() для актуального backend и CSV.
3. Каноническая реализация находится в core/: конфигурация, документы, BM25, история, HTTP-клиент, промпт, проверка результата и demo.
4. Поддержаны TXT/MD/CSV/JSON/DOCX/PDF и архив knowledge-base.zip. ID стабильны при неизменных имени и тексте. Источники содержат раздел/страницу, смещения относятся к извлечённому блоку.
5. ZIP не распаковывается на диск; проверяются пути, дубликаты, ссылки, размеры и зашифрованные записи. Неизвестные или пустые документы не считаются успешно обработанными.
6. Использован BM25Plus с одинаковой нормализацией. Кандидаты и соседи помещаются в ограниченный контекст. Индекс не хранит пользовательских диалогов.
7. Qwen-клиент получает URL/ключ/модель из окружения, не добавляет /v1, не следует редиректам и не меняет провайдера. Ограничены время, число повторов и параллельность.
8. Модель выбирает точные цитаты. Код проверяет ID и вхождение цитаты в источник, затем составляет ответ. Структурная проверка не объявляется проверкой полноты или релевантности ответа.
9. Demo включается только CORE_DEMO=true; вымышленный стенд Альфа не описывает продукт Energytool. В ответах и предупреждениях есть явная маркировка.
10. solution.py использует то же ядро, сохраняет строковые ID, историю текущего CSV-кейса и непустые ответы. Общий дедлайн передаётся ядру; результаты атомарно записываются по мере завершения.
11. Подготовлен сборщик плоского ZIP с преобразованием импортов, без веба и данных.
12. Добавлены раздельные установки для платформенного кандидата и веба, инструкция и синтетический CSV для запуска. Dockerfile расширен только установкой зависимостей ядра.

RAG-зависимости также добавлены в веб-lock, поэтому существующая установка `requirements-web.txt` не ломает импорт ядра. Новые pytest-сценарии находятся в `tests/core/`, прежний unittest-проход backend сохранён. Workflow не менялся; для полной проверки ядра отдельно запускается `python -m pytest -q`.

## Не подтверждено и что предстоит

- Реальный knowledge-base.zip, demo CSV, sample_submission.zip и оригинальный whitelist не получены. Нельзя утверждать, что обработаны все фактические форматы базы.
- Настоящий Qwen и API организаторов не вызывались. Корректность маршрутов эмбеддингов/реранкера не предполагается.
- Платформенный ZIP не принят и не оценён платформой. Её Python, ресурсы и полный лимит 20 минут нужно проверить по оригинальному регламенту и реальному запуску.
- Docker локально не установлен; изменение Dockerfile проверено чтением, сборка образа приложения не выполнялась. Штатные PostgreSQL-проверки backend выполнены в GitHub Actions; отдельный ручной запуск PostgreSQL и внешнее развёртывание не проводились.
- Нет OCR, сложного восстановления PDF-таблиц и неподтверждённых форматов Excel/HTML. Скан без текста отклоняется с диагностикой.
- Нет векторного поиска, реранкера, оценённого порога отказа, семантического судьи, пользовательского кэша или обучения модели. Это последующие измеряемые улучшения.
- Цитирование не доказывает правильность выбора фрагмента, полноту условий, уместность уточнения и качество консультации. Нет оценки на 18 demo-вопросах организаторов, потому что их нет.
- Длинная история сокращается по целым репликам с предупреждением. Факты давних сообщений и исправления нужно дополнительно проверять на настоящей модели.
- Синхронный парсинг/индексирование не прерываются насильно внутри одной операции; бюджет проверяется между документами и после индекса. Реальные ресурсы требуется измерить; искусственно завышать лимиты без замеров нельзя.
- Технические запасные ответы в CSV обеспечивают формат и полноту ID, а не корректную консультацию при отказавшем API. Счётчики ошибок следует смотреть отдельно от успешного статуса записи CSV.

## Следующий рабочий этап

Получить материалы от участницы по базе и настройки Qwen, отключить demo, изучить архив и исходные зависимости, проверить неизменённый пример организаторов, сопоставить реальный формат истории, разметить источники и измерить поиск/ответы/ресурсы. После этого улучшать извлечение, границы фрагментов и промпт; гибрид и реранкер сравнивать отдельными экспериментами.
