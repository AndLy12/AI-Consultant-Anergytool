# HTTP API v1 — МТС Energytool

Актуальный контракт backend с аккаунтами, 13 ноября 2026.
Источник схем входа — backend/app.py; интерактивная схема — /docs,
машинная — /openapi.json. Базовый адрес локального запуска: http://localhost:8000.
Старые /api/session, /api/chats и SSE не поддерживаются.

## Вход и права

POST /api/auth/register и POST /api/auth/login принимают JSON:

```json
{"email":"client@example.test","password":"Test-password-123"}
```

Регистрация возвращает 201, вход — 200:

```json
{"user":{"id":"uuid","email":"client@example.test","is_staff":false},"csrf_token":"session-specific-token"}
```

Email нормализуется в нижний регистр, длина 3–254; пароль 10–128 символов,
его пробелы не обрезаются. Принадлежность email не проверяется, писем и
восстановления пароля нет. Роль сотрудника назначается только оператором через CLI.

Сервер устанавливает HttpOnly-cookie energytool_session, SameSite=Lax, срок
7 дней. COOKIE_SECURE=true применяется при HTTPS. Токен cookie не возвращается
в JSON. На другом устройстве нужно войти в тот же аккаунт.

Для защищённых изменений передавайте заголовок X-CSRF-Token из register/login/me.
GET /api/auth/me возвращает user и CSRF текущей сессии. POST /api/auth/logout
требует CSRF, возвращает 204 и завершает вход только на текущем устройстве.

Запросы браузера идут с того же origin; для Vite используется dev-proxy.
Если Origin присутствует и не совпадает с APP_ORIGIN, изменяющий запрос отклоняется.
Origin не заменяет cookie и CSRF. Ключи модели, user_id и роли клиент не назначает.
Неизвестные поля входных JSON запрещены.

## Диалоги и сообщения

| Метод | Путь | Результат |
| --- | --- | --- |
| POST | /api/dialogs | 201: новый диалог |
| GET | /api/dialogs | 200: массив собственных диалогов |
| GET | /api/dialogs/{id} | 200: диалог с messages |
| POST | /api/dialogs/{id}/close | 204: закрытие диалога |

Новый диалог в одной транзакции закрывает прежний активный диалог аккаунта.
Старый остаётся в архиве, новый имеет пустую историю. Чтение архива не открывает
его и не меняет контекст. Запись нового сообщения в закрытый диалог возвращает 409.

Диалог содержит id, user_id, status (active/closed), version, created_at.
Идентификаторы — строки UUID, время — ISO 8601 UTC. Списки пока без пагинации.

POST /api/dialogs/{id}/messages принимает:

```json
{"request_id":"00000000-0000-4000-8000-000000000001","content":"Как экспортировать отчёт?"}
```

request_id — UUID, создаётся клиентом один раз на попытку отправки.
content — непустой текст до 10 000 символов; внешние пробелы обрезаются.
Ответ синхронный, 200; потоковой передачи нет. Время ожидания зависит от ядра.

Ответ содержит id, dialog_id, request_id, role=assistant, content,
status=completed, sources, elapsed_ms, created_at, result_meta.
Поля action, summary_draft, core_status, missing_information и warnings также
развёрнуты на верхнем уровне ответа отправки. В GET истории они находятся в result_meta.

Источник содержит document_id, chunk_id, title, excerpt, section и page.
Frontend выводит content и excerpt как текст; они не являются доверенным HTML.
summary_draft — предложение резюме, а не созданная заявка.

Правила повторов:

- Тот же request_id и текст возвращают сохранённый ответ без нового вызова модели.
- Тот же ID с другим текстом — 409.
- Пока идёт другая генерация в этом диалоге — 409.
- При техническом сбое ядра — 503; пользовательское сообщение сохранено со статусом failed.
- После failed нужна новая попытка с новым request_id; старый ID вернёт 409.
- В контекст ядра попадают только завершённые обмены текущего диалога.
- После аварии при следующем старте processing помечается failed, модель сама не перезапускается.

## Карточка и подтверждение заявки

PUT /api/dialogs/{id}/application сохраняет черновик:

```json
{"full_name":"Тестовый Клиент","phone":"+7 000 000-00-00","company":"Тестовая компания","summary":"Вымышленный запрос"}
```

Ограничения backend: full_name 2–200 символов, phone 7–30 символов
и 7–15 цифр с допустимым оформлением (+, пробелы, скобки, дефисы),
company 1–300, summary 1–10 000. Внешние пробелы обрезаются.
Frontend может дополнительно проверять ФИО; backend сейчас проверяет его длину.

PUT возвращает 200 и карточку: id, dialog_id, четыре поля, status=draft,
version, consent_at, created_at. Каждое сохранение увеличивает version.
GET того же пути возвращает карточку либо 404, если она ещё не подготовлена.

После показа карточки пользователь явно подтверждает её:
POST /api/dialogs/{id}/application/confirm:

```json
{"version":1,"consent":true}
```

Сервер сравнивает version: устаревшая — 409, consent=false — 422.
Успех — 200 с той же карточкой, status=created и заполненным consent_at.
Повтор подтверждения актуальной версии возвращает тот же id; второй заявки нет.
Перезаписать созданную заявку через PUT нельзя (409).
Заявка хранится в БД, отправки в CRM нет. После неё консультация доступна.

## Проверка сотрудником

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | /api/staff/dialogs | Все диалоги, включая диалоги без заявки |
| GET | /api/staff/dialogs/{id} | Выбранный диалог с сообщениями |
| GET | /api/staff/applications | Все карточки, включая draft и created |

Нужна сессия аккаунта с is_staff=true. Обычному пользователю возвращается 403.
Маршруты владельца проверяют владельца даже для сотрудника; общий просмотр
выполняется только через отдельные staff-маршруты.

## Ошибки

Ответ ошибки — {"detail": ...}. Для HTTP-ошибок detail обычно строка,
для валидации входа — массив Pydantic с loc/msg/type; не следует разбирать
произвольный английский текст как стабильный машинный код.

| Код | Причина и действие клиента |
| --- | --- |
| 401 | Нет действующей сессии либо неверный вход: показать вход |
| 403 | Нет CSRF, неверный Origin или недоступна роль сотрудника |
| 404 | Объект не найден; для чужого и неизвестного диалога ответ одинаков |
| 409 | Конфликт запроса/состояния/версии: перечитать состояние |
| 422 | Неверные поля либо нет явного согласия |
| 429 | Лимит регистрации/входа: подождать |
| 503 | Технический сбой ядра либо неготовность /ready |

Лимит register/login: общий бюджет 15 попыток за 60 секунд на IP в одном процессе.
Публичная ошибка ядра не раскрывает его исключение, адрес/ключ провайдера.
Архитектура рассчитана на один backend-процесс; это не распределённый rate limiter.

## Диагностика и запуск

GET /health сохраняет прежний ответ: status, core_mode, core_demo, core_ready,
frontend (react/diagnostic). Он проверяет доступ к таблице пользователей.
GET /ready возвращает 200, если доступна текущая схема БД и загружено ядро,
иначе 503. checks содержит database/core; provider_checked=false означает,
что платный API во время проверки не вызывался. Stub/demo обозначены явно.
Docker healthcheck использует /ready. Проверка не измеряет качество ответов.
