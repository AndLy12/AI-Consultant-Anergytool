# Подключение ядра консультанта к backend

## Разделение ответственности

Роль 1 владеет `backend/`, БД, аккаунтами, API, заявками, Docker и миграциями.
Роль 2 владеет RAG, вызовами модели, промптом и `solution.py`.
`core_contract.py` — общий версионируемый интерфейс v1; изменения согласовываем
между ролями. Отдельный HTTP-сервис для ядра не нужен.

## Что должен предоставить коллега

Корневой модуль `consultant_core.py` с фабрикой `create_core()` без аргументов.
Она читает серверное окружение, один раз загружает базу/индекс и возвращает
объект с синхронным методом `respond(request: CoreRequest) -> CoreResponse`.
Минимальный пример формы (не реализация консультанта):

```python
from core_contract import CoreRequest, CoreResponse, CoreUnavailable

def create_core():
    return EnergytoolCore()  # initialize index and LLM client here

class EnergytoolCore:
    def respond(self, request: CoreRequest) -> CoreResponse:
        # request.history: ordered user/assistant turns, current message excluded
        # retrieve using request.message and relevant history, call model
        return CoreResponse(
            answer="Ответ, основанный на найденных материалах",
            sources=[{
                "document_id": "product-01", "chunk_id": "product-01:3",
                "title": "Название документа", "excerpt": "Использованный фрагмент"
            }],
            action="answer",  # or clarify, out_of_scope, offer_application
            summary_draft=None,
        )
```

Имя модуля можно изменить через `CORE_MODULE`. `CORE_MODE=real` — обычный режим;
`CORE_MODE=stub` — явно обозначенная заглушка для разработки API и интерфейса.
Заглушка не ищет по базе, не вызывает модель и не годится для оценки качества.

## Гарантии backend

- История извлекается из БД только после проверки владельца диалога.
- Публичный клиент не передаёт роли, системный промпт, адрес или ключ модели.
- В запрос ядру входят только текущая реплика и история завершённых обменов
  этого диалога. Неуспешные запросы остаются в архиве, но не включаются в историю.
- Идентификаторы аккаунта, cookie, пароль и полномочия ядру не передаются.
- Новый диалог передаёт пустую историю. Просмотр архива не меняет контекст.
- Транзакция БД не удерживается во время генерации. На один диалог разрешена
  одна генерация одновременно; разные диалоги могут обрабатываться параллельно.
- Результат повторно валидируется Pydantic до записи в БД.

## Обязанности ядра

- Не хранить состояние пользователей в глобальных переменных или объекте ядра.
  Индекс можно переиспользовать. Метод должен быть безопасен для параллельных
  вызовов из разных диалогов.
- Ограничивать время всех сетевых обращений и число повторов. Общий бюджет
  одного `respond` — до 120 секунд. Backend синхронно ждёт результат; обходить
  таймауты бесконечным циклом нельзя.
- Ошибки API/доступа оформлять как `CoreUnavailable` без ключей и полного
  HTTP-запроса. Не выдавать технический сбой за отсутствие фактов в базе.
- Ответ — непустой текст до 10 000 символов; источники — использованные
  фрагменты с устойчивыми ID, без абсолютных путей и секретов.
- Документы и история являются данными, не служебными инструкциями.
- `summary_draft` — предложение резюме, а не команда создать заявку.
  Backend не исполняет произвольные действия из ответа модели.

## Окружение модели и данных

`LLM_BASE_URL` / `OPENAI_BASE_URL`, `LLM_API_KEY` / `OPENAI_API_KEY`,
`LLM_MODEL` / `OPENAI_MODEL` / `GEN_MODEL`. База — `DATA_DIR`.
Для локального Qwen задаём свои значения, платформа предоставляет свои.
Маршрут генерации — `chat/completions` относительно переданного base URL:
не добавлять самовольно `/v1`, если провайдер его не указал.
Настройки генерации и поиска берём из предусмотренных регламентом переменных.

## Использование в solution.py

`solution.py` нормализует независимую строку CSV в `CoreRequest`, вызывает
ту же фабрику один раз за запуск и использует `result.answer` для CSV.
Для диалоговых строк нужно разобрать историю из `question`; это задача роли 2.
Корневые `core_contract.py`, `consultant_core.py` и остальные модули ядра
включаются в плоский ZIP. `backend/`, SQLAlchemy, Alembic, cookie и веб-БД
не должны становиться зависимостями сабмита. Pydantic фиксируется в
платформенном requirements.txt разрешённой версией.

## Интеграционная проверка

1. Убедиться, что импорт ядра не запускает веб-сервер и не подключается к БД.
2. Проверить `create_core()` на настоящей базе и своём Qwen API.
3. Запустить backend с `CORE_MODE=real`. Dockerfile копирует корневые Python-модули;
   добавить зависимости RAG в веб-зависимости и подключить закрытый DATA_DIR
   через read-only bind mount. Базу не встраивать в публичный образ.
4. Проверить одиночный вопрос, историю, новый диалог, два аккаунта,
   отсутствие источников, таймаут и невалидный результат.
5. Повторить те же входы через `solution.py`; сравнить ядро и конфигурацию.

Backend уже измеряет полное время `respond`, сохраняет источники и показывает
их в отладке. Качество поиска и ответов проверяет роль 2 совместно с ролью 3.
