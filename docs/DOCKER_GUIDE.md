# Docker на примере нашего backend

## Зачем он здесь

Без Docker разработчик устанавливает Python, создаёт .venv, ставит библиотеки,
выбирает каталог БД, запускает миграции и сервер. На другом компьютере может
оказаться другая версия Python или отсутствовать нужная системная библиотека.
Docker позволяет описать окружение в коде и запускать его одинаковым способом.
Он не исправляет ошибки приложения и не гарантирует перенос данных сам по себе.

## Пять основных понятий

| Понятие | В нашем проекте |
| --- | --- |
| Dockerfile | Инструкция сборки Linux-окружения с Python и приложением |
| Образ, image | Результат сборки: файлы окружения, библиотеки, код, настройки запуска |
| Контейнер | Запущенный экземпляр образа с отдельным процессом и файловой системой |
| Volume, том | Постоянное хранилище SQLite вне жизненного цикла контейнера |
| Compose | Описание сервисов, портов, настроек, томов и проверки готовности |

Один образ можно запускать несколько раз. Контейнеры при этом не обязаны
разделять данные. В нашем прототипе поддерживается один backend-процесс,
потому что восстановление запросов рассчитано на одну реплику.

## Это не то же самое, что .venv

.venv изолирует Python-пакеты, но использует Python и ОС компьютера.
Docker изолирует приложение вместе с Linux-библиотеками, интерпретатором,
файловой системой и настройками сети. Поэтому локальную .venv мы не копируем.
На Linux контейнеры используют ядро хоста; на macOS Linux-контейнерам требуется
Linux VM, которую обычно предоставляет Docker Desktop. Виртуальная машина
в этом случае является частью среды Docker, а не отдельной VM для каждого контейнера.

## Путь от файлов к работающему сайту

```text
Dockerfile + код + requirements-web.txt
                  |
              docker build
                  |
              Linux-образ
                  |
        docker compose up
                  |
       контейнер backend:8000
                  |
       /data → постоянный том app-data

Браузер → localhost:8000 на компьютере → порт 8000 контейнера → FastAPI
```

## Разбор Dockerfile

`FROM python:3.12-slim` задаёт исходное Linux-окружение с Python 3.12.
slim означает уменьшенный вариант образа. Это тег, а не неизменяемый хеш:
поставщик может выпускать обновления. Для строгого воспроизведения в будущем
можно закрепить digest; сейчас версии Python-пакетов закреплены в requirements.

`WORKDIR /app` задаёт рабочий каталог внутри образа. Он не является каталогом
/app на твоём Mac. Команды RUN и относительные COPY дальше используют его.

`COPY requirements-web.txt .` сначала копирует только список зависимостей.
`RUN pip install ...` выполняется при сборке, а не при каждом запуске контейнера.
Если код поменялся, а список зависимостей остался прежним, Docker может
переиспользовать слой установки пакетов и ускорить сборку.

Последующие COPY помещают backend, неизменённый core, миграции и корневые
Python-модули в образ. Это копия на момент сборки: изменение файла на Mac
само по себе не меняет контейнер. Для новой версии надо пересобрать образ.
Bind mount с автоматическим обновлением кода — отдельный вариант для разработки,
мы его в проверке чистого запуска не используем.

Пользователь app с UID 10001 создаётся при сборке. `USER app` означает, что
приложение запускается без root. Владельцем /data становится этот пользователь,
чтобы SQLite могла создавать файл БД и соседние служебные файлы WAL.

`EXPOSE 8000` документирует внутренний порт. Сам по себе он не делает сайт
доступным с компьютера: публикацию порта задаёт Compose.

`CMD` выполняется при старте контейнера. Сначала Alembic обновляет схему БД;
только после успеха запускается Uvicorn. `exec` заменяет промежуточную оболочку
процессом сервера: сигнал остановки доходит до Uvicorn для корректного завершения.

## Два разных localhost и два порта

Внутри контейнера 127.0.0.1 означает сам контейнер. На компьютере — компьютер.
Это разные сетевые пространства. Поэтому Uvicorn слушает 0.0.0.0 внутри
контейнера, а Compose публикует порт на 127.0.0.1 компьютера.

Запись `127.0.0.1:8000:8000` читается так:

- 127.0.0.1 — интерфейс компьютера, доступный локально;
- первый 8000 — порт на компьютере;
- второй 8000 — порт сервера в контейнере.

Если порт занят, можно задать APP_PORT=8001. Внутренний порт останется 8000.
Также нужно APP_ORIGIN=http://localhost:8001 для проверки Origin браузерных запросов.
Контейнерный localhost не позволяет обратиться к API, запущенному на самом Mac;
такое подключение требует отдельного адреса, например поддерживаемого Docker
Desktop host.docker.internal. Публичный Qwen API использует свой обычный URL.

## Почему данные не должны жить только в контейнере

У контейнера есть изменяемый слой файлов. Простая остановка и запуск того же
контейнера не удаляют его, но удаление и создание нового контейнера теряют
данные этого слоя. Поэтому важные данные выносят в том.

В Compose `app-data:/data` связывает Docker volume с /data внутри контейнера.
DATABASE_URL указывает SQLite на /data/energytool.db. Удаление контейнера
не удаляет этот том. Реальное имя тома обычно содержит имя Compose-проекта.

Обычный `docker compose down` удаляет контейнер и сеть проекта, сохраняя том.
Следующий up подключит его обратно. `down --volumes` дополнительно удаляет
том с БД. Это команда очистки данных, а не обычный способ перезапуска.

Том не является резервной копией. Потеря диска/VM Docker или ручное удаление
тома могут уничтожить данные. Для настоящей эксплуатации нужны отдельные backup.
SQLite с WAL надо резервировать согласованно, а не копировать произвольный файл
в момент записи. Замена DATABASE_URL на PostgreSQL не переносит накопленные записи.

## .env, окружение и .dockerignore

В нашем Compose .env необязателен: без него запускается тестовый backend.
Compose использует .env для подстановок `${...}`; секция environment перечисляет,
что именно получает контейнер. Просто положить .env рядом с кодом недостаточно,
чтобы все его значения автоматически оказались внутри процесса приложения.

Окружение не шифруется. Оператор Docker может прочитать настройки контейнера;
вывод docker compose config тоже может раскрывать значения. Ключи не включаем
в Git, Dockerfile, образ, скриншоты и публикуемые логи. Для серьёзного внедрения
понадобится согласованное управление секретами.

.dockerignore исключает .git, .venv, .env, БД, исходные материалы и ненужные
каталоги из контекста сборки. Контекст — файлы, доступные сборщику Docker.
Исключение полезно даже если Dockerfile пока явно не копирует такие файлы.

## Как узнать, что приложение действительно готово

Контейнер может находиться в состоянии running, хотя приложение ещё запускается
или не готово отвечать. Healthcheck обращается к /health и проверяет API и схему БД.
`docker compose up --wait` ждёт успешной проверки. Готовность /health не означает,
что настоящее ядро или Qwen уже работают: у заглушки тоже есть здоровый backend.

`restart: unless-stopped` разрешает Docker перезапускать завершившийся контейнер,
пока оператор не остановил его. Неуспешный healthcheck сам по себе не означает
автоматического перезапуска: это отдельный статус готовности.

## Команды для повседневной работы

```bash
docker compose up --build --wait
docker compose ps
docker compose logs --tail=100 backend
docker compose logs --follow backend
docker compose exec backend python -m backend.manage grant-staff --email reviewer@example.test
docker compose restart backend
docker compose down
```

up --build собирает образ при необходимости и запускает сервис; ps показывает
состояние; logs читает stdout/stderr; exec выполняет команду внутри уже работающего
контейнера. restart перезапускает существующий контейнер: новый код он не собирает.
Для изменённого кода используют up --build, а не только restart.

## Как устроена наша проверка чистого окружения

GitHub CI получает чистый checkout и не устанавливает Python-зависимости
приложения на хост. Скрипт стандартной библиотеки запускает Docker build без кеша,
затем регистрацию, сообщение и заявку через HTTP. Проверяет непривилегированного
пользователя и отсутствие .env/.venv/.git/Данные в образе.

После этого контейнер удаляется без удаления тома и создаётся заново.
Скрипт проверяет аккаунт, историю, заявку и старую сессию после пересоздания.
Это проверка настоящего контейнера; она не является проверкой настоящей LLM.

Тестовый проект имеет уникальное имя. Его одноразовый том удаляется в конце;
том обычного приложения не используется. На Mac без Docker этот скрипт запустить
нельзя: CI не означает, что Docker установлен на компьютере разработчика.

## Что изменится после подключения ядра

Потребуются CORE_MODE=real, модуль ядра, зависимости поиска, настройки API и
закрытый read-only доступ к базе знаний. API-ключи приходят при запуске, не при
сборке. Ни модель Qwen, ни база PostgreSQL не появляются внутри нашего образа
автоматически. Qwen вызывается по API; SQLite пока является файлом, а не отдельным
контейнером. При PostgreSQL это будет отдельный сервис или доступная серверная БД.
