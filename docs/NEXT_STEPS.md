## 2. Какой продукт нужно получить

Пользователь описывает задачу, консультант при необходимости задаёт уточнения, находит основания в базе Energytool и даёт применимую рекомендацию. При согласии пользователя приложение помогает сформировать заявку.

Обязательные свойства по разделам 2, 7 и 10 исходной инструкции:

1. Характеристики, цены, условия, сроки и обещания экономии подтверждаются материалами базы.
2. При достаточных данных консультант отвечает по существу. Ненужная анкета перед каждым ответом не требуется.
3. Если оснований нет, консультант прямо сообщает об ограничении.
4. Исправления пользователя заменяют прежние значения; смена темы учитывается.
5. Пользователь может продолжить консультацию без телефона и без оформления заявки.
6. История сохраняется и для диалогов без заявки.
7. Новый диалог имеет собственный контекст. Просмотр архива не присоединяет старый разговор к текущему.
8. Созданная заявка подтверждается записью backend, а не одним текстом модели.
9. Консультант не превращается в систему настройки приборов или выдачи неподтверждённых технических инструкций.

Нужны два способа использования общего ядра: веб-приложение и отдельный `solution.py` для проверки платформой. Веб-хранилище и браузер не должны быть обязательными для запуска `solution.py`.

## 5. Ваша реализация: следующая контрольная точка backend

**Цель:** в пределах текущего диалога сохраняются подтверждённые данные клиента; по его явному согласию backend создаёт одну заявку. Повтор запроса не создаёт вторую. Отказ от телефона не останавливает чат.

### B1. Добавить управляемое обновление структуры SQLite

**Зачем:** появятся новые сущности, существующие диалоги должны сохраниться.

Действия:

- [ ] Добавить последовательное обновление схемы, используя версию БД; сейчас используется `user_version=1`.
- [ ] Подготовить новые таблицы для фактов, состояния заявки и созданной заявки.
- [ ] Сохранить связи с владельцем и диалогом и включённые внешние ключи.
- [ ] Проверить повторный запуск обновления и запуск на пустой БД.

**Приёмка:** БД первой точки обновляется без потери диалогов и сообщений; повторный запуск ничего не дублирует.

### B2. Хранить факты текущего разговора отдельно от текста истории

Основание: раздел 10 исходной инструкции.

Предлагаемые поля факта: `chat_id`, имя поля, значение, признак подтверждения, ссылка на сообщение-основание, время обновления. Для неизвестного поля хранить явное отсутствие значения.

Действия:

- [ ] Определить необходимый минимум: задача клиента, компания, ФИО, телефон и другие согласованные параметры консультации.
- [ ] Разделять предложение модели и подтверждённые пользователем сведения.
- [ ] Связывать факт с текущим диалогом и сообщением-основанием.
- [ ] При исправлении заменять активное значение; старое не должно попадать в актуальное резюме.
- [ ] Проверять владельца при каждом чтении и обновлении.
- [ ] Не переносить профиль автоматически из архива в новый контекст.

**Приёмка:** после «компания А» → «поправка, компания Б» используется Б. В соседнем диалоге этих сведений нет. Неизвестный телефон остаётся неизвестным.

### B3. Реализовать состояния заявки

Обязательные состояния по инструкции:

| Состояние | Что означает | Условие перехода |
|---|---|---|
| Не предложена | Пользователь получает консультацию | Появился уместный повод предложить заявку |
| Предложена | Пользователь видит добровольное предложение | Пользователь согласился обсудить оформление |
| Сбор данных | Запрашиваются недостающие сведения | Необходимые сведения собраны |
| Проверка | Пользователь видит итоговые поля и резюме | Backend проверил данные и получено согласие на создание |
| Создана | Существует сохранённая запись с ID | Только после успешной транзакции БД |

**Важно:** согласие обсудить заявку не подменяет согласие на её создание. Возврат к консультации возможен до создания; отказ от контактов не должен блокировать ответы.

**Приёмка:** модель не может произвольным полем ответа перескочить сразу в «создана». Все переходы проверяет приложение.

### B4. Добавить проверку полей и создание заявки

Обязательные сведения из инструкции: **ФИО, телефон, компания и резюме**. Дополнительно backend проверяет согласие и принадлежность сессии.

Действия:

- [ ] Согласовать формат телефона и правила ошибок. Проверка формата не означает подтверждение владения номером.
- [ ] Проверить непустые обязательные поля, разумную длину и допустимую структуру.
- [ ] Показать пользователю сведения и резюме перед записью.
- [ ] Записать подтверждение согласия в связи с конкретной заявкой и её данными.
- [ ] Если данные после подтверждения изменились, повторно показать итог и получить подтверждение актуальной версии.
- [ ] Выполнить запись транзакционно; защитить её от повторной отправки и параллельных запросов.
- [ ] Возвращать ID и статус только после успешной записи.

**Приёмка:** нет согласия или одного обязательного поля — записи нет. Повтор того же запроса возвращает ту же заявку. Чужая сессия не может прочитать или создать заявку для данного диалога.

**Граница:** сохраняем заявку в прототипе. Подключение CRM, отправка писем и сообщение «менеджеру отправлено» в эту задачу не входят.

### B5. Расширить API для фактов и заявки

Предлагаемый вариант; имена нужно закрепить в контракте v0.2:

| Метод | Возможный путь | Назначение |
|---|---|---|
| GET | `/api/chats/{id}/facts` | Текущие факты и неизвестные поля |
| PATCH | `/api/chats/{id}/facts` | Исправление подтверждаемых пользователем сведений |
| GET | `/api/chats/{id}/lead-draft` | Состояние и проект заявки |
| POST | `/api/chats/{id}/lead-draft/confirm` | Проверка актуальной версии и согласия |
| POST | `/api/chats/{id}/leads` | Недублирующаяся запись проверенной заявки |
| GET | `/api/chats/{id}/leads/{lead_id}` | Результат в пределах прав текущей сессии |

С клиента не принимаются доверенные роли, системный промпт, ключи, произвольный адрес модели или права доступа. Любые новые поля результата модели требуют обновления текущей строгой схемы: сейчас дополнительные поля запрещены.

### B6. Проверить следующую точку до подключения настоящей модели

Минимальные сценарии для №1 и №3:

- [ ] Консультация продолжается после отказа оставлять телефон.
- [ ] Уже известные сведения не запрашиваются заново без причины.
- [ ] Исправление заменяет активное значение.
- [ ] Незнакомое поле остаётся неизвестным, а не заполняется предположением.
- [ ] Без согласия запись не создаётся.
- [ ] Изменение данных после подтверждения требует новой проверки.
- [ ] Повтор и параллельная отправка создают одну заявку.
- [ ] Ошибка БД не приводит к сообщению об успешном создании.
- [ ] Чужая сессия не получает факты, проект или готовую заявку.
- [ ] После перезапуска факты и заявка сохранены.
- [ ] Новый диалог не наследует архивный контекст.

**Зависимости:** B1 → B2 и B3 → B4 → B5; B6 проверяет итог. Контракт B5 согласуется заранее, параллельно с B1. Настоящее ИИ-ядро для этих проверок не требуется.

Порядок: извлечение текста → метаданные → смысловые фрагменты → BM25 → найденный контекст → модель → проверка результата.

- Не воспринимать инструкции внутри документа как команды приложения.
- Установить ограниченные повторы, таймауты и параллельность; учитывать повторы SDK вместе с повторами приложения.

**Приёмка:** на размеченных примерах показаны вопрос, найденный фрагмент, ответ и его основание; для отсутствующего ответа корректно обозначено ограничение.

- [ ] Подключить адаптер в точку запуска. Сейчас стандартный запуск подключает только stub; одного изменения `CORE_MODE` недостаточно.

**Приёмка:** в вебе получен настоящий ответ по базе с проверяемым источником; второй диалог изолирован; техническая ошибка не маскируется консультацией.

### AI4. Сделать ранний платформенный сабмит

Не ждать завершения оформления веба: после baseline собрать отдельный `solution.py`.

Правила из разделов 12–13 инструкции, подлежащие сверке с регламентом:

| Пункт | Требование |
|---|---|
| Вход | `DATA_DIR`, по умолчанию `data`; `questions.csv` с `id,question`, UTF-8; база `knowledge-base.zip` |
| Диалоги | Каждая строка — независимый тест; ответ на последнюю реплику с учётом истории этой строки |
| Выход | `submission.csv` в рабочем каталоге, UTF-8, ровно `id,answer` |
| Полнота | Один непустой ответ для каждого исходного ID; без дублей, новых номеров и лишних колонок |
| Длина | Не более 10 000 символов; обычная цель — до 150 слов |
| ZIP | До 128 МБ; `solution.py`, разрешённый `requirements.txt` и необходимые корневые `.py` без внешней папки |
| Состав | Без данных, вопросов, индексов, конфигураций, `.whl`, frontend, Docker и веб-БД |
| Индекс | Строится из переданной базы в текущем запуске; нельзя полагаться на прежний кэш |
| Установка | `pip install` из `solution.py` запрещён; зависимости устанавливает платформа |
| Ресурсы | Весь запуск до 20 минут, 8 CPU, 16 ГБ RAM |
| Попытки | 5 сабмитов в день на команду, сброс в 00:00 МСК |

**Особенность текущей структуры:** `core/` пока является пакетом для веб-интеграции. Сборщик платформенного ZIP должен подготовить корневые Python-модули с рабочими импортами. Простое архивирование текущего проекта не создаёт совместимый сабмит.

**Особенность зависимостей:** текущий веб использует Pydantic 2.14.3, а в инструкции для платформы перечислена 2.14.2. `requirements-backend.txt` нельзя автоматически использовать как платформенный `requirements.txt`. Общее ядро и сборку нужно проверить в разрешённой среде; сейчас базовый контракт на dataclasses не зависит от Pydantic.

**Приёмка:** ZIP распакован в пустое окружение, прогон создаёт корректный CSV без веб-сервера; затем платформа фактически принимает и оценивает сабмит. Нахождение в очереди не считать полученной оценкой.

### AI5. Улучшать качество по измерениям

После baseline: извлечение и границы фрагментов → инструкции и история → сравнение с bge-m3 и гибридным поиском → при необходимости реранкер или дополнительная проверка.

Не внедрять все альтернативы одновременно. Для изменения фиксировать дефект, гипотезу, один существенный фактор, результат повторного сценария и общего набора, задержки и новые ошибки. Неудачный эксперимент не объявлять улучшением.
