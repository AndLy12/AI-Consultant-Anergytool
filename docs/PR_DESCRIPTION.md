# Подготовка backend к воспроизводимому запуску через Docker

## Задача

Обеспечить запуск веб-прототипа из чистой копии репозитория: без локальной
`.venv`, заранее созданной БД, API-ключей и исходных документов кейса.
Проверить, что аккаунты, история и заявки сохраняются при пересоздании контейнера.

Рабочая ветка: `backend/role1-integration`. Целевая ветка: `main`.

## Контекст существующего backend

Следующая функциональность уже опубликована в `main` предыдущими коммитами;
она описана здесь как основа проверяемого приложения, а не новые изменения PR:

- Регистрация и вход по email/паролю, хеширование паролей Argon2id.
- Серверные сессии устройств с HttpOnly-cookie; история аккаунта доступна с разных устройств.
- Создание диалога, сохранение сообщений, закрытие и просмотр архива.
- Новый диалог начинает чистый контекст, история предыдущих остаётся в БД.
- Проверка владельца диалога и заявки; отдельные административные API для сотрудника.
- CSRF-проверка изменяющих запросов и проверка Origin.
- Сохранение карточки заявки с ФИО, телефоном, компанией и резюме.
- Создание заявки только после явного согласия с актуальной версией карточки.
- Повтор подтверждения возвращает прежний ID заявки, а не создаёт дубль.
- Сохранение сообщений при ошибке ядра, обработка повторов `request_id`.
- Хранение источников ответа и времени обработки для отладки.
- SQLite, переносимый слой SQLAlchemy и миграции Alembic; драйвер PostgreSQL.
- Адаптер исходного интерфейса Данька `async answer(history)` и контракт `respond(request)`.
- Простой веб-интерфейс для технической проверки; основной frontend — зона Даши.

## Изменения текущего PR

### Dockerfile

- Зависимости устанавливаются внутри Linux-образа из зафиксированного `requirements-web.txt`.
- Приложение работает от непривилегированного пользователя `app`, UID 10001.
- Каталог `/data` подготовлен для записи SQLite и подключения постоянного тома.
- Перед стартом применяются миграции `alembic upgrade head`.
- Uvicorn запускается через `exec`, чтобы корректно получать сигнал остановки контейнера.

### Docker Compose

- Для первого запуска не требуется создавать `.env`: предусмотрены значения по умолчанию.
- До подключения настоящего ядра используется явно обозначенный `CORE_MODE=stub`.
- `.env` остаётся способом переопределить настройки; ключи не встраиваются в образ.
- Порт публикуется только на `127.0.0.1`; его можно изменить через `APP_PORT`.
- SQLite хранится в именованном томе `app-data`, отдельно от контейнера.
- Добавлены healthcheck API/БД и время на корректное завершение приложения.

### Чистая сборка и CI

- Добавлен workflow `Docker clean start` для отдельной Linux-машины GitHub Actions.
- Скрипт `scripts/docker_smoke.py` использует только стандартную библиотеку на хосте.
- Образ собирается с обновлением базового образа и без кеша слоёв.
- Проверяются регистрация, отправка сообщения и подтверждение тестовой заявки.
- Контейнер удаляется и создаётся заново без удаления тома.
- После пересоздания проверяются вход с другого устройства, история, заявка,
  прежняя сессия и отсутствие дубля при повторном подтверждении.
- Проверочный Compose-проект получает уникальное имя; очистка относится только
  к его одноразовым ресурсам, а не к обычной базе приложения.
- Расширен `.dockerignore`: локальные окружения, ключи, БД и материалы кейса
  не должны попадать в контекст сборки.

## Ядро Данька и границы интеграции

Каталог `core/` в рамках этой работы не изменяется.
Текущий Docker-прогон проверяет backend с явной заглушкой.
Он не подтверждает качество RAG, доступность Qwen или готовность реального ядра.
В ветке `knowledge-base` на момент проверки находится инструкция, а не реализация ядра.

## Как проверить

Из корня чистой копии репозитория с установленным Docker Compose:

```bash
docker compose up --build --wait
```

Открыть `http://localhost:8000`, зарегистрироваться, создать диалог,
отправить сообщение и подтвердить карточку с вымышленными контактами.

Проверить сохранность данных:

```bash
docker compose down
docker compose up --wait
```

Повторно войти в тот же аккаунт и открыть сохранённый диалог и заявку.
Обычный `down` сохраняет том; `down --volumes` удаляет БД и для этой ручной проверки не нужен.

Полный автоматический Docker-прогон из отдельной чистой копии:

```bash
python scripts/docker_smoke.py
```

## Ограничения

- Регистрация прототипа без писем подтверждения и восстановления пароля — согласовано.
- Реальные CRM, почта и авторизация МТС не подключены.
- PostgreSQL можно выбрать через `DATABASE_URL`; смена URL не переносит данные SQLite.
- Docker-прогон не проверяет нагрузку и настоящее качество консультации.
- Код и настройки направляются в рабочую ветку; слияние с `main` — после проверки владельцем.
