# Каждый проверяет: работа без локального Qwen и LM Studio

Для Ани и коллеги три локальная модель не обязательна. Владелец проекта — Данёк
(автор запроса) — тоже проводит проверки, а не только объединяет код.
Это рабочие обязанности в этой группе; нумерация технических зон проекта не меняется.

## Что кому проверять

| Кто | Без модели | На готовых ответах | При доступной модели |
|---|---|---|---|
| Данёк (ты) | Тесты ядра, разбор истории, поиск и упаковка | Все критические дефекты, проигрыши и спорные выводы; повторный разбор части оценок ребят | Генерация baseline/кандидата, живые диалоги, реальные API/CSV и замеры |
| Коллега три | Наборы, unit-тесты, источники в поиске, полнота ID и отчётов | Независимое сравнение A/B, прямота ответа, история, классификация ошибок | Повтор спорных случаев через согласованный доступ, если он предоставлен |
| Аня | Проверка документов и критериев до генерации | Числа, единицы, ограничения, обещания, резюме и повторные вопросы | Новые ручные сценарии через доступный интерфейс, если он предоставлен |

Каждый сначала оценивает свою выборку самостоятельно. Критические случаи проверяют
минимум двое; дополнительно все трое размечают общие 10 сценариев для согласования
критериев. Расхождения разбирают по источнику. Результат не принимают большинством
голосов без проверки основания. Данёк не должен быть единственным проверяющим
собственного исправления.

## Самый простой режим: документы и готовый пакет

Без Python, Qwen и LM Studio можно читать вопросы, историю, ответы и источники
и заполнять таблицу замечаний. Данёк организует один реальный прогон и передаёт
обоим проверяющим одинаковый пакет в отдельной папке вне Git:

- `questions.csv`: ID, вопрос и история; многострочные поля корректно экранированы.
- `answers-A.csv` и `answers-B.csv`: одинаковые ID, сопоставляемые ответы без имён версий.
- `sources.jsonl`: для каждого ID/варианта — реально использованные фрагменты,
  заголовки и ID. Их нужно экспортировать из сохранённых результатов; обычного
  CSV id,answer недостаточно, чтобы восстановить источники конкретной генерации.
- `criteria.csv`: заранее определённые критерии и ссылки на разрешённые источники.
- `passport.json`: хеши файлов, реальные модели/параметры, коммиты, время и счётчики
  сбоев. Соответствие A/B хранить отдельно до первой независимой оценки.
- Копия разрешённых документов для проверки контекста, если у ребят её ещё нет.
- Пустая таблица оценки: `id,turn,reviewer,variant,verdict,severity,claim,source,reason`.

Это состав пакета, который надо подготовить при следующем прогоне, а не сообщение
о том, что свежие ответы уже сгенерированы. Секреты, cookie, HTTP-заголовки,
ключи и персональные данные реальных клиентов в пакет не входят. Если источники
из старого прогона не сохранены, это отмечается как пробел доказательств.

Готовые ответы позволяют проверять содержание. Они не измеряют текущую задержку
модели и не доказывают работоспособность нового кода. Отдельно подписывать
«проверен сохранённый ответ», «mock-тест», «новый реальный вызов».

## Режим с Python: проверки без API

В подготовленном окружении из корня репозитория:

```powershell
.venv/Scripts/python.exe -X utf8 -m pytest -q
.venv/Scripts/python.exe scripts/check_core_knowledge.py --data-dir knowledge-base-work/data --questions knowledge-base-work/data/demo_questions.csv --output work/team-quality/offline-search.json
.venv/Scripts/python.exe scripts/build_core_submission.py --output work/team-quality/check-only.zip
```

Пути к базе/вопросам заменить своими при необходимости. Для первой команды нужны
тестовые и веб-зависимости проекта, не только requirements.txt конкурсного ZIP;
использовать инструкции установки репозитория. Для второй нужны документы, но не
ключ или сервер модели. Она проверяет наличие контекста и его ID, не смысл ответа.
Третья собирает архив, не отправляет его. Не включать CORE_DEMO для имитации
реальной оценки: демонстрационный режим не проверяет качество Qwen.

Проверка тестов подготовки базы запускается отдельно из `knowledge-base-work`:

```powershell
../.venv/Scripts/python.exe -X utf8 -m pytest tests -q
```

Если Python нет, начать с ручного режима: это полноценная проверка содержания,
установка модели для неё не нужна.

## Генерация централизованно

Новые ответы получать на машине с настроенным API, например у Данька. Передать
ему новый набор вопросов; получить пакет с ответами и паспортом. Для живой цепочки
следующий вопрос должен учитывать реально полученный предыдущий ответ.
Просто запуск LM Studio ещё не означает готовность: проверить загруженную модель,
сервер, контекст и выполнение реального запроса. В этом изменении документации
состояние запущенного сейчас LM Studio не проверялось.

Если позже нужен самостоятельный запуск ребят, использовать согласованный
доступ к уже настроенному API или доступный чат приложения. Не требуется
устанавливать ту же модель каждому; не открывать порт LM Studio в интернет
и не пересылать общий ключ в MD ради такого доступа. Пока доступа нет,
готовый пакет остаётся основным режимом. LLM-судья тоже требует API;
его отсутствие не блокирует ручную оценку по источникам.

## Личный список проверок для тебя

1. Повторить найденную ошибку на 6v и подтвердить исправление на тех же входах.
2. Самому прочитать минимум 10 общих сценариев, все критические ошибки и проигрыши.
3. Сверить каждый спорный тезис с источником, а не только с оценкой LLM.
4. Провести отдельную цепочку с отказом от продукта, коррекцией числа и возвратом
   к теме; проверить актуальное резюме без выдуманных контактов.
5. На машине с моделью проверить реальные API/CSV, очередь, таймауты и время;
   на готовом ZIP повторить smoke, сверить ID и счётчики ошибок.
6. Получить независимую оценку коллеги три и Ани до решения о выпуске.
   Не исправлять их оценки задним числом: сохранять расхождение и его разбор.
