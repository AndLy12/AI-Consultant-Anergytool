# Данёк (ты): координация, интеграция и выпуск

Ты — №2, Данёк. Помимо доработки ядра, твоя задача — объединить свои изменения,
проверки коллеги три и смысловую приёмку Ани в одну проверяемую версию.
Общая цель и условия — [ROADMAP_100.md](ROADMAP_100.md).
Backend, API, хранение, согласие и границы безопасности остаются зоной №1;
ты проверяешь интеграцию, а изменения backend согласовываешь с ответственным №1.
Имя этого файла сохранено ради ранее переданных ссылок.

Ты также проверяешь качество самостоятельно: минимум 10 общих сценариев,
все критические ошибки и проигрыши, затем реальные API/CSV и готовый ZIP.
Подробный [личный список и режим работы без модели у ребят](CHECK_WITHOUT_QWEN.md).
Ане и коллеге три не нужно ставить локальный Qwen: передай им одинаковый пакет
реальных ответов с историей и источниками для независимого разбора.

## 1. Раздать задачи и исходную точку

Твоя инструкция — TASK_2_DANYOK.md; коллеге три передать TASK_3_QA.md,
Ане — TASK_5_ANYA.md, обоим — весь каталог team-6v.
Все стартуют с `5bf4d22afa9f7dab52b9de565b90f30e3b7885f3`.
Сохранить оригинальный ZIP 6v отдельно с SHA из README. Не пересобирать его
поверх: новый ZIP может получить другую контрольную сумму из-за метаданных.
Настройки модели/ключи и закрытые материалы передавать отдельно от Git.

Порядок запуска: коллега три замораживает критерии и исходные ответы; Данёк
воспроизводит дефект отказанных продуктов и делает первый минимальный патч.
Аня проверяет критерии по первоисточникам; ты проверяешь общий контракт
и возможность повторить API/CSV, привлекая №1 при изменении backend.

## 2. Ветки и объединение

Ветка сохранённого релиза — `codex/core-v6`. Она сохраняет текущую ветку ядра;
известный локально origin/main имеет 7 собственных коммитов после расхождения,
ядро — 8. Общий предок: `eec073b08b4c9f822a043b03903fe34db27d1a09`.
Смешивать их до фиксации исходной версии нельзя: получится другой кандидат.
Ниже команды создания рабочих веток в отдельных checkout, а не одновременно
в одной рабочей папке:

```powershell
git switch -c codex/core-intent-rag 5bf4d22afa9f7dab52b9de565b90f30e3b7885f3
```

Для коллеги три вместо имени ветки — `codex/core-quality-tests`.
В интеграционном checkout владельца после получения обеих веток:

```powershell
git switch -c codex/core-quality-integration codex/core-v6
git merge --no-ff codex/core-quality-tests
git merge --no-ff codex/core-intent-rag
```

Если команда работает через origin, сначала получить опубликованные коллегами
ветки и использовать их фактические ссылки `origin/...`. Не выполнять merge
несуществующей ветки или случайной версии с похожим именем. Документационный
коммит после 5bf4d22 тоже нужно передать ребятам: его содержит `codex/core-v6`.

Новые тесты могут выявить дефект baseline; объединять их с исправлением на
интеграционной ветке. В main попадёт только прошедшая все проверки комбинация.
Не делать force-push общей ветки, не перезаписывать чужие файлы и не разрешать
смысловые конфликты автоматическим выбором ours/theirs. Перед интеграцией с текущим
main сначала выполнить fetch, прочитать отличающиеся изменения и контракт;
после merge на отдельной интеграционной ветке повторить обязательные проверки.
Не считать локальные ссылки origin актуальными без fetch. Исходный коммит 6v
и его ZIP при этом остаются неизменными.

## 3. Обязательные проверки

Из корня репозитория:

```powershell
.venv/Scripts/python.exe -X utf8 -m pytest -q
```

Из отдельного рабочего каталога `knowledge-base-work`:

```powershell
../.venv/Scripts/python.exe -X utf8 -m pytest tests -q
```

Для 6v исходный результат — 169 и 20. Не фиксировать это число как вечное:
новые осмысленные тесты увеличат его. При общем запуске из неверного каталога
возможна коллизия модулей scripts, поэтому два запуска разделены.

С подготовленными реальными настройками модели из корня:

```powershell
.venv/Scripts/python.exe scripts/check_live_api_csv.py --protocol knowledge-base-work/data/role3-review/role3-web-csv-protocol.json --output work/team-candidate/api-csv
.venv/Scripts/python.exe scripts/build_core_submission.py --output work/team-candidate/core-knowledge-submission-6v.zip
```

Первая команда требует локальных закрытых материалов роли 3 и доступного API;
она действительно вызывает модель. Её не заменяют unit-тесты. Пять протокольных
сценариев — минимум совместимости, не вся оценка качества.

Проверить по отдельности:

- Точный CoreRequest и история одинаковы в API и CSV; текущая реплика не добавлена
  дважды. Случайные формулировки ответа могут различаться при одинаковом смысле.
- Права и история изолированы; повтор запроса не вызывает модель повторно;
  резюме модели не создаёт заявку без явного согласия.
- CSV содержит ровно id,answer; строки UTF-8, ведущие нули ID сохранены,
  все входные ID присутствуют один раз. Ответы непустые, в рамках публичного контракта.
- 401/403, 429, 5xx, таймауты, неверный JSON и переполнение контекста учтены;
  незавершённая дополнительная проверка видна отдельно от технического отказа.
- ZIP содержит только 13 разрешённых файлов в корне. Нет базы документов,
  эталонов, .env, ключей, frontend, backend или БД. Зависимости соответствуют регламенту.
- В отдельной папке распакованного ZIP импорты работают с платформенными
  зависимостями; реальный smoke и финальные наборы запускаются на упакованном коде,
  а не только на исходниках с доступом к репозиторию через PYTHONPATH.
- Суммарное время и ресурсные ограничения проверены по актуальному регламенту;
  локальное окружение и отличие модели платформы записаны.

## 4. Паспорт кандидата и решение об отправке

Для каждой сборки завести отдельный каталог, не затирать предыдущую. В паспорте:
коммит/чистота дерева, имя релиза, SHA-256 ZIP и входных данных, список файлов,
точные зависимости, модель/квантование/контекст, параметры окружения без секретов,
даты, команды, метрики поиска/содержания/судьи/времени, счётчики сбоев,
неустранённые ошибки, ссылки на полный разбор коллеги три.

Сначала принять все условия ROADMAP_100. Если остаётся критическая ошибка,
потерянные строки или неясное время — вернуть на исправление. Если выигрыш только
на многократно использованных demo, получить свежую независимую проверку.
Сам по себе высокий локальный балл не основание тратить попытку сайта.

До отдельного решения владельца сайт не трогать. Имя отправляемого релиза можно
сохранить 6v, как договорились; различать внутренние сборки по коммиту и SHA,
а не переименованием одной и той же папки без журнала. После отправки записать
фактический балл и архив, не переписывая старые прогнозы задним числом.

## 5. Что смотреть ежедневно

Короткая общая таблица: дефект → ответственный → коммит → тест до/после →
независимый разбор → время → принято/возвращено. Первая очередь: неправильный
продукт из отрицания; затем повторные вопросы/история; затем основания, поиск
и проверка фактов; оптимизация — после подтверждения качества. Отклонённые
эксперименты сохранять в отчётах с причиной, не объединять их в релиз автоматически.

Путь к 100 состоит из этих измеряемых циклов. Обоснованного обещания ровно
100 на неизвестном наборе нет; контроль владельца — требовать доказательства
прогресса и не принимать красивую локальную цифру за официальный результат.
