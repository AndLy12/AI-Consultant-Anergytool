# №2 — Данёк: повысить качество ядра

Данёк — это ты, автор запроса. Помимо ядра, ты координируешь работу коллеги три
и Ани и собираешь кандидата по [чек-листу интеграции](TASK_1_OWNER.md).

Помимо исправлений, сам проверяешь общие сценарии и критические случаи.
Ребятам без локального Qwen готовишь пакет ответов с источниками по
[инструкции совместных проверок](CHECK_WITHOUT_QWEN.md).

База: коммит `5bf4d22afa9f7dab52b9de565b90f30e3b7885f3`, релиз 6v, сайт 49,861.
Общий порядок и критерии — [ROADMAP_100.md](ROADMAP_100.md).
Ветка: `codex/core-intent-rag`. Работать в отдельном checkout/worktree.

## Твоя зона

`core/dialogue.py`, `retrieval.py`, `prompts.py`, `validation.py`, `engine.py`,
`llm.py`, `config.py`, соответствующие тесты ядра и при необходимости `solution.py`.
В первую очередь менять только файлы, необходимые текущему исправлению.
Backend, БД и UI не переделывать. Общий `core_contract.py` менять только совместно
с №1 — владельцем проекта; сохранить контракт и русские пояснения.

## Первая поставка: намерение без ложных обязательных источников

1. Воспроизвести оба запроса из [аудита](../../core/SITE_REVIEW_6v_2026-11-14.md)
   на неизменной 6v. Сохранить поисковую строку, отобранные разделы и required.
2. Выделить активное намерение и явные исключения до BM25 и обязательных якорей.
   Не ограничиваться понижением рейтинга после поиска: ошибочный required переживает реранкер.
3. Учитывать смену мнения по последней реплике клиента; не превращать предыдущий
   ответ ассистента в утверждённый факт клиента. Сохранять нужные контекстные условия.
4. Покрыть тестами отказ от продукта, «не X, а Y», отрицательный вопрос о свойстве,
   двойное отрицание, повторное включение темы, ссылку «вернёмся к первому варианту»,
   несколько реально нужных продуктов и полностью положительные контрольные запросы.
5. Отдельно проверить «единый кабинет» без слов «учёт электроэнергии» — нужная
   платформа должна находиться по смыслу, без произвольного назначения всех таких запросов.

Минимальные пары: «панели не нужны, нужен учёт» / «учёт не нужен, нужны панели»;
«не отказываемся от солнечной станции» / «отказываемся от солнечной станции»;
«нужно менять SIM?» / «SIM менять не нужно?»; вопрос о резерве солнечной станции.
Для свойства отрицание не исключает сам продукт. Не удалять все предложения с «не».

Поставка: один небольшой коммит с причиной ошибки, тестами, результатом до/после
по источникам и реальными ответами на воспроизведениях. Не объявлять улучшение
поиска ростом официального балла.

## Вторая поставка: ответ и история

- Убрать безусловный следующий вопрос. Сначала ответ; уточнение только если
  оно меняет решение. Не спрашивать сведения, уже сообщённые клиентом.
- Последнюю коррекцию факта использовать в текущем выводе и резюме. Отдельно
  тестировать противоречия мощности, потребления, типа объекта и схемы учёта.
- Сохранять ограничения и единицы рядом с числом; не упрощать ценой неверного обещания.
- Не выдавать технический сбой за отсутствие знаний. Отсутствие основания для
  одного утверждения не должно автоматически уничтожать весь полезный ответ.
- Проверить контраст: вопрос о поддержке двух тарифов / запрос настройки для
  конкретного парка; общее свойство / индивидуальный расчёт; резюме / стоимость.

Поставка: отдельный коммит, разбор новых ответов коллегой три, отсутствие регрессий
на 18 demo и критических сценариях. Не переписывать эталоны ради прохождения.

## Третья поставка: поиск и проверка оснований

Сначала по журналу коллеги три исправить конкретные пропуски разделов и условий.
Затем отдельными экспериментами сравнить варианты BM25, реранкера и гибрида
с BGE-m3. Проверить реальную доступность/формат API, кеширование индекса, размер
контекста и отсутствие новых зависимостей вне регламента. При отказе дополнительного
сервиса поведение должно быть ограничено по времени и отражено в отчёте.

Оценивать значимые утверждения по источникам: число, применимость, гарантия,
срок, бесплатность. Сравнить повторную проверку включённой и выключенной;
записывать исправленные, пропущенные и внесённые ошибки. Не наращивать цепочку
вызовов или строковых замен без измеренной пользы. Недоступный EMB_MODEL не
должен превращать исправление намерения в неработающее решение.

## Четвёртая поставка: скорость после качества

Замерить этапы, очередь, p50/p95 и суммарное время. Подбирать лимиты ответа,
контекста и параллельность по одному, сохраняя общий дедлайн. Проверить таймауты,
429/5xx, неверный JSON, обрезку, context_length и поведение необязательной проверки.
Уменьшение задержки принимается только вместе с сохранением содержания.

## Что передать на общую приёмку

Для каждого изменения: коммит, объяснение поведения, список изменённых файлов,
тесты, ID исправленных сценариев, реальные ответы/источники, время, известные
проигрыши и способ отката. Генератору не показывать финальный закрытый набор QA.
Не изменять паспорт исходного ZIP 6v, не отправлять кандидатов на сайт самостоятельно.
