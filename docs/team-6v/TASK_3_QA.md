# №3 — коллега три: независимые проверки качества

Локальный Qwen и LM Studio не обязательны. Основной режим — наборы, offline-тесты
и независимый разбор готовых реальных ответов. Если API недоступен, команды
с `--execute` ниже выполняет Данёк, а тебе передаёт результаты и источники.
См. [проверки без локальной модели](CHECK_WITHOUT_QWEN.md).

База: коммит `5bf4d22afa9f7dab52b9de565b90f30e3b7885f3`, 6v с официальными 49,861.
Ветка: `codex/core-quality-tests`. Общая программа — [ROADMAP_100.md](ROADMAP_100.md).

## Твоя зона

Новые проверочные сценарии, отчёты, инструменты
в `eval/`, новые файлы тестов и отдельные QA-скрипты. Факты и применимость источников
проверяет Аня по TASK_5_ANYA.md; ты поддерживаешь наборы и измерения. Для исключения конфликтов
новые автотесты складывать, например, в `tests/core/test_intent_quality.py`;
изменения существующих тестов Данька согласовывать. Production-файлы ядра не менять:
нашёл ошибку — передай воспроизведение Даньку. Комментарии/docstring — на русском.

Закрытые вопросы, эталоны, ответы и материалы организаторов хранить вне Git,
например в `work/team-quality/`. В Git — инструменты и синтетические допустимые
примеры. Рабочие материалы роли 3 передавать отдельно: они не входят в checkout.

## Первая задача: заморозить оценку до просмотра ответов

1. Подготовить 60–100 сценариев с распределением из общей программы. Для диалогов
   указать все ходы; не считать 5 повторов одного вопроса пятью независимыми примерами.
2. До генерации записать обязательные факты, применимые условия, допустимые
   альтернативы и запрещённые обещания. Для каждого — документ, раздел, точная
   выдержка. При конфликте источников явно записать неопределённость.
3. Отложить примерно 20 сценариев для финала. Передать Даньку только разработческую
   часть и описание классов ошибок. Зафиксировать хеши/время наборов и критериев.
4. Прогнать неизменную 6v и сохранить её ответы. Нового кандидата сравнивать
   с теми же исходными ответами, входами и окружением.

18 demo и уже просмотренные 8 heldout — разработческие проверки. Название
«holdout» в старом файле не возвращает независимость после исправлений по нему.

## Вторая задача: разделить причины ошибок

Для каждой строки вести:

| Поле | Что записывать |
|---|---|
| Идентичность | scenario_id, номер хода, коммит, хеш входов/корпуса, модель и параметры |
| Вход | Текущая реплика, факты истории, положительное намерение, исключённые продукты |
| Поиск | Нужный факт найден? Неверный required? Источник альтернативный, но применимый? |
| Ответ | Прямота, правильность фактов, полнота условий, лишний/повторный вопрос, верное действие |
| Основания | Для спорного утверждения — точная цитата и объяснение соответствия/противоречия |
| Ошибка | Техническая / поиск / история / выдуманный факт / пропуск условия / нерелевантность / стиль |
| Серьёзность | Критическая, существенная, небольшая; правило серьёзности фиксируется заранее |
| Производительность | Время этапов/всего, число вызовов, retries, review_incomplete |
| Решение | Пройден/не пройден/не хватает оснований; имя проверившего и обоснование |

Критическая ошибка: опасное для решения клиента ложное обещание, неправильный
порог применимости, потеря существенного ограничения, раскрытие чужих данных,
техническая подмена ответа. Спорные случаи разобрать с Аней по первоисточнику,
а не по уверенности генератора или судьи.

## Третья задача: покрыть перенос и устойчивость

- Все группы из матрицы ROADMAP: продуктовые числа, ограничения солнечного резерва,
  OCR и поверка, бесплатность, функции платформы, неизвестные данные.
- Минимальные пары с отказом/включением продукта и отрицанием свойства; синонимы,
  опечатки, единицы, разговорные формулировки и короткие ссылки на историю.
- Цепочки по 2–6 ходов с реальными предыдущими ответами, исправлением числа,
  сменой темы и возвращением. Фиксированный transcript проверять отдельно:
  он не заменяет живой диалог.
- Недостаток источников, конфликт фактов, чужие данные/служебные инструкции,
  инструкция в документе, отказ от контактов. Фикстуры менять только в копии контекста,
  не в исходной базе и не в общем индексе.
- API: независимые аккаунты/диалоги, повтор запроса, отсутствующее согласие,
  отсутствие общей пользовательской памяти; подготовить сценарии для Данька; изменения backend согласовать с №1.

## Реальные вызовы и существующие инструменты

Настройки модели и DATA_DIR подготовить через окружение, CORE_DEMO=false.
Начать с smoke, затем critical и только после разбора полный набор. Примеры
из корня репозитория (вместо Python из PATH допустима `.venv/Scripts/python.exe`):

```powershell
python scripts/role3_acceptance.py --review knowledge-base-work/data/role3-review --suite smoke --execute --source-revision 5bf4d22
python scripts/role3_acceptance.py --review knowledge-base-work/data/role3-review --suite critical --critical-repeats 3 --execute --source-revision 5bf4d22
python scripts/role3_acceptance.py --help
python scripts/judge_answers.py --help
```

Для кандидата подставлять его настоящий SHA, а не 5bf4d22. Не использовать
имя модели в отчёте, отличающееся от реально отвечавшей модели.
`obtained_pending_review` означает только получение ответа, не смысловую приёмку.
Автотест с mock, детерминированное воспроизведение ответа и новый реальный вызов
помечать раздельно. Неполный прогон не включать в таблицу как успешно пройденный.

## Судейство и отчёт

Сравнивать 6v и кандидата в двух порядках A/B, скрыв имена версий от судьи.
По возможности использовать отдельную от генератора модель и ручной разбор
спорных случаев. Указывать baseline, модель судьи, rubric/hash и размер набора.
Формула в существующем скрипте — 0,7 MatchRate + 0,3 WinRate; ничьи исключаются
из WinRate, полностью ничейный набор получает 0,5. Ошибки судьи не становятся
поражениями: они отмечаются, исключаются и делают оценку неполной.

Сохранить выигрыши, ничьи и проигрыши по категориям, позиционную нестабильность,
ошибки источников и конкретные причины. Для доли прошедших критерии ответов
показывать размер и интервал неопределённости; для попарного выигрыша — устойчивость
на независимых сценариях, например bootstrap по сценариям, а не по ходам/повторам.
Баллы локального судьи не объявлять прогнозом сайта.

Поставка №1: замороженный набор и исходные результаты 6v. Поставка №2: журнал
ошибок с минимальными воспроизведениями. Поставка №3: сравнительный отчёт кандидата
и решение по каждому условию выпуска. Финальный контроль раскрыть только после
фиксации кандидата; при найденном дефекте исправить и отметить потерю независимости.
