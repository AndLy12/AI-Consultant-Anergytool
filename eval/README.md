# Сравнение готовых консультаций

Из корня проекта используйте Python с зависимостями ядра и доступный OpenAI-совместимый API. Для генерации и оценки задайте LLM_BASE_URL, LLM_MODEL и LLM_API_KEY. Для полностью локальной проверки укажите адрес LM Studio на 127.0.0.1 и имя загруженной модели. Если сервер работает без авторизации, достаточно непустого локального значения ключа. Модель судьи можно сменить между командами через те же переменные.

~~~powershell
$env:CORE_DEMO = "false"
$env:DATA_DIR = (Resolve-Path knowledge-base-work/data).Path
$env:MAX_WORKERS = "1"
python solution.py --questions "$env:DATA_DIR/demo_questions.csv" --output work/candidate.csv
python scripts/judge_answers.py --questions "$env:DATA_DIR/demo_questions.csv" --reference "$env:DATA_DIR/demo_output.csv" --baseline work/eval-v8/answers.csv --candidate work/candidate.csv --output work/comparison.json
~~~

В этом рабочем каталоге сохранены ответы v8. В новом checkout базовый CSV получают запуском сохранённой версии solution.py на тех же вопросах, базе и локальном API. Сохраняйте ответы вместе с отчётом, названием модели, настройками и версией ZIP. Следующие версии сравнивайте с одной сохранённой базовой версией. Для более строгой проверки используйте ответы предыдущего сильного кандидата. Генератор читает только вопрос и базу. Эталон передаётся отдельно судье.

Сначала проверьте rows, completed, technical_failures, review_incomplete, unprocessed и answer_statuses в файле рядом с CSV. Во время исполнения файл уже содержит заготовки для всех ID. Для оценки используйте завершённый прогон. failure_counts учитывает окончательные причины сбоев строк после повторов.

Судья независимо получает обе перестановки пары, выбирает лучшую сторону и величину преимущества. Код переводит выбор в оценку ответу A с шагом 0,25. Скрипт переводит оба раунда в шкалу кандидата и усредняет их. Match Rate равен среднему по оценённым вопросам. В Win Rate учитываются победы и поражения относительно 0,5, при одних ничьих он равен 0,5. Итог равен 0,7 × Match Rate + 0,3 × Win Rate. Неполные пары показаны как исключённые; такую проверку CLI завершает ненулевым кодом. В JSON сохраняются причины решения по каждому раунду.

Закрытые вопросы, ответы baseline и промпт судьи организаторов недоступны. Локальный балл характеризует указанную пару версий. Повторная доработка по 18 примерам делает этот набор отладочным. Для оценки переноса используйте отдельные диалоги и разметку до просмотра ответов. Отдельный прогон разметки Ани измеряет попадание фактов в контекст.

Для проверки действий на 30 размеченных диалогах Ани используйте те же настройки модели. Отчёт включает статус, ответ и ID оснований для ручной проверки. Проверочное вложение KB11 применяется только к копии найденного фрагмента.

~~~powershell
python scripts/check_core_actions.py --cases "$env:DATA_DIR/review/cases.jsonl" --output work/actions.json
~~~


## Материалы роли 3

Переданный закрытый архив сохранён локально в work/role3-private, рабочая копия разметки —
в knowledge-base-work/data/role3-review. Журналирование из архива подключено через
scripts/role3_acceptance.py. Исправлены работа часового пояса на Windows и проверка
происхождения источников при коротких ID в промпте. Сохранены исходные фиксация независимого
набора и хеши всех входов.

~~~powershell
python scripts/role3_acceptance.py --review knowledge-base-work/data/role3-review --suite all --critical-repeats 3 --execute --include-context-fixtures --budget-seconds 2400 --source-revision <хеш-кандидата>
python scripts/check_live_api_csv.py --protocol knowledge-base-work/data/role3-review/role3-web-csv-protocol.json --output work/api-csv
~~~

Первый запуск включает 36 критических повторов, 30 основных сценариев, 18 официальных
примеров, 8 независимых сценариев и 7 шагов живых цепочек. В живых цепочках используется
фактически полученная история. Отдельная проверка API создаёт временную SQLite БД,
проходит регистрацию и HTTP-обмен, проверяет идемпотентный повтор, затем воспроизводит
тот же запрос через CSV с новым вызовом настоящей модели. Совпадение входов проверяется
строго. Тексты консультаций и ограничения оцениваются содержательно.

В журнале obtained_pending_review означает получение ответа. Автоматическая проверка
происхождения цитат оставляет смысловую оценку открытой. Результаты прочтения ответов
следует хранить в assessments.csv с конкретным обоснованием и именем проверяющего.
Число повторов следует отличать от числа независимых входов.


Судья выбирает A, B или ничью и величину преимущества. Код переводит выбор
в 0, 0.25, 0.5, 0.75 или 1, проверяет согласованность ничьей и повторяет сравнение
с перестановкой сторон. Итог использует формулу регламента 0.7 MatchRate + 0.3 WinRate.
Ошибка вызова исключает вопрос с явным счётчиком excluded и ненулевым кодом завершения.
Совпадение формулы не воспроизводит скрытую модель и baseline организаторов.
Сохранённые старые отчёты с числовым score_a напрямую из модели относятся к прежней
методике; сравнивать их с новой нужно после повторного судейства.

Восемь отложенных сценариев роли 3 после первого прогона и исправления ошибки H05
стали частью разработки. Их повторное прохождение проверяет исправление, но уже
не является независимой оценкой переноса на неизвестные вопросы.


Ошибка context_length означает превышение контекста модели. Она не отключает
согласованный JSON-формат и управление мышлением для последующих запросов.
review_incomplete в отчёте CSV считает сохранённые первоначальные ответы, для которых
не завершилась дополнительная проверка. Этот счётчик следует разбирать отдельно
от technical_failures.

Текущий кандидат поставляется как core-knowledge-submission-6v.zip. Промежуточные
архивы и незавершённые CSV в work/ являются диагностикой. Для сравнения выбирайте
только завершённый CSV с полным отчётом, нулевыми unprocessed и technical_failures.
