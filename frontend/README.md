# МТС Energytool — задание на frontend

Дата: 12 ноября 2026 года. Статус: инструкция перед началом реализации.

Ветка `frontend` создана только для этого задания. При её создании здесь нет кода приложения. Начало реализации и способ получения кода из `main` нужно согласовать с лидом; эта ветка имеет отдельную начальную историю и не предназначена для обычного слияния с `main` без подготовки.

## 1. Основание и команда

Требования составлены по `CODEX_AI_CONSULTANT_INSTRUCTIONS.md` от 10 ноября 2026 года, `DECISIONS.md` от 12 ноября и последним уточнениям владельца проекта.

При расхождении с ранними планами ориентируемся на согласованные решения из `DECISIONS.md`. Документы про ПСБ к нашему продукту не относятся. Названия новых API ниже описаны как операции: точные пути и поля утверждает backend-разработчик вместе с лидом.

В команде четыре человека:

| Роль | Ответственность |
|---|---|
| Лид / ядро | Модель, поиск по базе, инструкции консультанта, качество ответов, общий Python-код для веба и платформы, интеграция |
| Backend | Аккаунты, серверные сессии, права, БД, API, диалоги, проверка и запись заявок, запуск |
| Frontend — это задание | Экраны, состояния, взаимодействие с API и проверка пользовательского пути |
| База знаний | Разбор документов, проверенные факты и источники, вопросы для оценки качества, описание пробелов |

## 2. Какой продукт делаем

Веб-консультант по МТС Energytool. Пользователь описывает задачу, получает ответ по базе знаний, при необходимости уточняет данные и по собственному желанию оформляет заявку.

Интерфейс должен позволять продолжать консультацию без телефона и без заявки. Если модель не нашла подтверждённый ответ, пользователь должен видеть понятное ограничение или уточнение.

Не придумываем характеристики, цены, экономию и сроки. Инструкции по настройке приборов не являются назначением консультанта. Для демонстрации используем вымышленные контакты.

## 4. Экран входа и регистрации

По решениям 4–6 из `DECISIONS.md`:

- Регистрация по email и паролю; email используется как логин.
- Вход в существующий аккаунт.
- Понятные ошибки формата и результата операции согласно API.
- Кнопка показа/скрытия пароля и корректные подсказки полей.
- После входа — загрузка диалогов аккаунта, а не пустая локальная история браузера.
- Выход завершает сессию текущего устройства. Не сообщать, что выполнен выход со всех устройств.

**Не добавлять:** письма подтверждения email, восстановление пароля по почте, обещание проверки принадлежности адреса. Эти функции прямо исключены текущим решением владельца.

Вход МТС относится к будущему внедрению. Кнопку «Войти через МТС» не выдавать за работающую интеграцию.

## 5. Основной экран консультации

Нужны следующие элементы:

1. Список диалогов аккаунта: активный разговор и доступный архив.
2. Заголовок и статус открытого диалога.
3. История сообщений с различимыми репликами пользователя и консультанта.
4. Поле ввода, отправка, состояние ожидания и понятная ошибка.
5. Карточки подтверждающих источников, если они есть в ответе.
6. Уточняющий вопрос или перечень недостающих сведений, если этого требует ответ.
7. Доступ к проекту заявки без принуждения к оформлению.
8. Явные действия «Новый диалог», «Закрыть диалог», «Выйти».

Сообщения отображать безопасным текстом или обработанным Markdown. HTML и скрипты из сообщения, базы или ответа модели исполняться не должны.

Не показывать пользователю служебные промпты, сырой JSON модели, API-ключи, отладочные трассировки и технические параметры поиска.

## 6. Жизненный цикл диалогов

По решению 7: **у аккаунта один активный диалог**. Новый закрывает прежний активный разговор. Состояние определяет сервер, включая работу с двух устройств.

| Действие | Ожидаемое поведение |
|---|---|
| Создать новый диалог | Сервер закрывает предыдущий активный и создаёт пустой активный контекст |
| Явно закрыть диалог | Он становится архивным и остаётся доступным для просмотра |
| Открыть архив | Показывается история; отправка в закрытый контекст недоступна |
| Начать заново из архива | Создаётся новый пустой контекст; архив не копируется в историю модели |
| Обновить страницу | Состояние и история загружаются с сервера |
| Войти на другом устройстве | Доступна история того же аккаунта; сервер сообщает актуальный активный диалог |
| Закрыть вкладку браузера | Само по себе не считается надёжным закрытием диалога на сервере |

Если на другом устройстве активный диалог был закрыт или заменён, интерфейс должен обработать серверный конфликт: обновить состояние и объяснить, что произошло. Не продолжать отправку в устаревший диалог.

## 7. Отправка, повтор и ошибки

- Для одного логического сообщения создавать один `request_id`, если такое поле закреплено контрактом.
- При сетевом повторе использовать прежний ID и прежний текст; не создавать дубликат нажатием «Повторить».
- На время отправки предотвращать случайные повторные нажатия.
- Не терять набранный текст при ошибке.
- Различать ожидание, успешный ответ, прерванную обработку и отказ сервера принять запрос.
- Истечение сессии переводит к повторному входу с понятным уведомлением.
- Таймаут, 429, 5xx и недоступность API показывать как техническую проблему. Это не ответ «в базе нет информации».
- После переподключения получать сохранённое состояние с backend.

Способ доставки ответа согласовать с backend. В ранней версии SSE передаёт уже готовый проверенный ответ; это не живой поток токенов модели. Не изображать неподтверждённую генерацию и не полагаться на конкретные события до согласования контракта.

По решению 11 backend работает одним процессом; после его перезапуска прерванные `processing`-сообщения переводятся в `failed`. Интерфейс должен показать возможность согласованного повтора, а не бесконечное ожидание.

## 8. Источники и границы ответа

Источник должен позволять понять, откуда взялся факт: название документа, раздел или страница, подтверждающий фрагмент. Показывать только поля, реально возвращённые API.

- Не создавать ссылку на документ из догадки или имени, придуманного frontend.
- Не подставлять случайный источник, если ответ пришёл без него.
- Не делать закрытые файлы публичными ради кнопки «Открыть».
- Если просмотр документа будет реализован, получать содержимое через согласованный backend с проверкой доступа. Не считать этот метод уже существующим.
- Статусы «нужно уточнение», «нет достаточных данных», «непрофильный запрос» отображать понятно и без вывода сырого технического кода.
- Не выводить «достоверность 95%», если backend не имеет согласованного способа её расчёта.

Frontend показывает проверенный результат сервера. Проверка истинности ответа и соответствия цитаты базе остаётся задачей ядра и подготовки базы.

## 9. Карточка заявки и согласие

По решениям 8–9 модель готовит ответ и черновик резюме, а backend проверяет права и выполняет запись.

Карточка содержит ФИО, телефон, компанию и резюме задачи. Пользователь видит, исправляет и подтверждает сведения перед созданием.

Последовательность:

1. Добровольное предложение оформления.
2. Сбор только недостающих данных. Известные контакты не спрашивать заново без необходимости.
3. Показ итоговой карточки.
4. Явное согласие на создание по актуальной версии карточки.
5. Запрос записи с согласованным ID повтора и версией карточки.
6. Показ результата только после успешного ответа backend с реальным ID заявки.

Обязательные состояния:

- Заявка ещё не предложена.
- Предложена, пользователь может отказаться.
- Идёт сбор данных.
- Данные готовы к проверке.
- Запись выполняется.
- Создана.
- Ошибка записи или версия карточки устарела.

Если пользователь изменил данные после подтверждения, прежнее согласие не использовать для новой версии. При конфликте показать актуальные данные и предложить проверить их снова.

**Одна заявка на диалог.** Повтор возвращает тот же ID. После создания пользователь может продолжить общение. Обновление или отмена созданной заявки не считается готовой функцией без отдельного API и задачи.

Сообщать «Заявка сохранена» допустимо после фактической записи. «Отправлена в CRM» или «Менеджер получил» недопустимо: таких интеграций сейчас нет.

## 10. Сессии и безопасность на клиенте

- Серверная сессия передаётся через HttpOnly-cookie. Не дублировать токен в localStorage или JavaScript-переменных приложения.
- Для изменяющих запросов использовать CSRF-механизм, который реализует backend; согласовать выдачу и передачу CSRF-токена.
- Не заменять CSRF одним наличием cookie или ID диалога.
- Историю и права определяет backend. Не отправлять с клиента служебные роли, системный промпт, адрес модели или ключ.
- Не сохранять реальные контакты и полные ответы в аналитике или общедоступных логах.
- В Git публикуется код интерфейса; в нём нет секретов и закрытой базы.
- В разработке согласовать общий origin/dev-proxy. Настройка CORS не должна обходить серверные проверки доступа.

## 11. Что согласовать с backend до интеграции

| Группа | Необходимые операции и данные |
|---|---|
| Аккаунт | Регистрация, вход, текущий пользователь, выход текущего устройства, ошибки |
| CSRF | Как получить токен, в каком заголовке передавать, что делать после истечения |
| Диалоги | Список, активный диалог, новый, явное закрытие, архив, начало заново |
| Сообщения | Формат текста, ID повтора, статус обработки, повтор failed-сообщения |
| Ответ | Текст, статус, источники, уточнения и предупреждения |
| Заявка | Черновик, редактирование, версия, согласие, создание, повтор и ID результата |
| Конфликты | Изменения с другого устройства, закрытый чат, устаревшая карточка |
| Запуск | Порт, origin, сборка, подключение к Docker-поставке |

Отдельный сервис ядра не нужен: frontend обращается к единому Python-backend. Браузер не обращается напрямую к Qwen API.

В разработке используется согласованный собственный OpenAI-совместимый Qwen API, на платформе — API организаторов. Провайдер, ключ и модель задаются серверным окружением; при сбое приложение не должно самовольно менять провайдера. Публичный хостинг, CRM, почта и авторизация МТС сейчас не подключены.

## 12. Порядок работы после разрешения на реализацию

1. Утвердить контракт и собрать макеты основных экранов и состояний.
2. Сделать вход/регистрацию и оболочку приложения на согласованных моках.
3. Сделать чат, список, архив и явное закрытие.
4. Добавить источники, уточнения, ошибки и повтор.
5. Добавить карточку заявки, версии и согласие.
6. Подключить реальный backend по согласованному контракту.
7. Вместе с лидом проверить ответ настоящего ядра по базе.
8. Проверить итоговую сборку и обновить краткие инструкции запуска.

Работа на моках должна быть явно обозначена. Моковый ответ не является проверкой доступа к модели или продуктовой достоверности.

## 13. Приёмка frontend

- [ ] Пользователь регистрируется, входит и выходит с текущего устройства.
- [ ] Нет неработающих обещаний подтверждения email, восстановления пароля и авторизации МТС.
- [ ] История доступна после повторного входа и на другом устройстве.
- [ ] Новый диалог закрывает предыдущий активный на уровне аккаунта.
- [ ] Явное закрытие и архив работают; архив не присоединяется к новому контексту.
- [ ] Устаревшее состояние после действий с другого устройства обрабатывается.
- [ ] Вопрос проходит через backend и возвращает ответ; источники читаемы.
- [ ] Повтор сообщения не создаёт дубликат, текст при ошибке сохраняется.
- [ ] Без телефона и заявки можно продолжать консультацию.
- [ ] Карточка показывает актуальные сведения, исправления и согласие.
- [ ] Старая версия карточки не подтверждается молча; повтор записи возвращает ту же заявку.
- [ ] После создания заявки можно общаться дальше.
- [ ] Чужая история и заявка не доступны через интерфейс; серверные запреты обработаны.
- [ ] HTML/скрипты из текста не исполняются; секреты и контакты не попадают в публичную отладку.
- [ ] Основные сценарии доступны с клавиатуры и на узком экране; ошибки и ожидание заметны.

Результат сдачи участника: исходники интерфейса после отдельной отмашки, инструкция запуска, список проверенных сценариев и известных ограничений.

## 14. Как писать код и комментарии

Пожелание владельца: понятные имена и спокойные комментарии обычным языком. Комментарий объясняет смысл блока, нетривиальную причину или ограничение; не пересказывает каждую строку.

Примеры полезных пояснений: «При повторе сохраняем ID запроса, чтобы сервер не записал сообщение второй раз»; «Архив показываем только для чтения: его история не должна стать новым контекстом».

Пояснения должны помогать другому разработчику понять решение и проверить его. Короткие комментарии рядом с важным блоком полезнее длинного вступления к каждому файлу.
