# Интерфейс участника №4

Основной веб-чат клиента: вход в аккаунт, консультация с источниками, сброс
контекста, история диалогов, заявка менеджеру, режим отладки и экран проверки
для сотрудника.

Стек: React 19 + TypeScript + Vite, обычный CSS без UI-фреймворка. Версии
зафиксированы в `package.json`. Актуальный контракт: `../docs/BACKEND.md`
и `/openapi.json`. Авторизация: `/api/auth/*`, затем CSRF-токен в изменяющих
запросах. Диалоги: `/api/dialogs/*`, заявки: `/api/dialogs/{id}/application`.
Старое API v0.1 заменено. Временная страница проверки в `backend/static/`
остаётся у роли №1 как образец вызовов. Ключи LLM в браузер не передаются.

## Запуск для разработки

Нужен Node.js 20+ и запущенный backend роли №1.

1. Поднять backend из корня репозитория:

   ```bash
   docker compose up --build --wait
   ```

   Порт задаётся в `.env`. Пример для 8001: `APP_PORT=8001`,
   `APP_ORIGIN=http://localhost:8001`, `CORE_MODE=stub`.

2. Запустить интерфейс:

   ```bash
   cd frontend
   npm install
   npm run dev
   ```

   Открыть http://localhost:5173.

Если backend работает на другом порту, скопируйте `.env.example` в `.env`
и поправьте `VITE_API_TARGET` и `VITE_API_ORIGIN`. Секретов в этих файлах нет
и быть не должно.

### Почему нужен dev-прокси

Backend принимает изменяющие запросы только со своего `APP_ORIGIN` и отвечает 403
на чужой Origin. Dev-сервер Vite работает на другом порту, поэтому `vite.config.ts`
проксирует `/api` и `/health` и подменяет заголовок `Origin` на адрес backend.
Это повторяет боевую схему, где собранная страница раздаётся с того же origin,
что и API, и не требует изменений в backend.

## Сборка

```bash
npm run build      # проверка типов и сборка в frontend/dist
npm run preview    # локальный просмотр собранной версии
npm run typecheck  # только проверка типов
```

Готовая сборка рассчитана на раздачу с того же origin, что и API; способ раздачи
согласуется с ролью №1. Каталог `dist` не коммитим.

Inline-скрипты и inline-стили не используем: CSP backend
(`script-src 'self'; style-src 'self'`) их запрещает. Внешние шрифты и CDN
по той же причине не подключаем.

## Что уже работает

- вход и регистрация, восстановление сессии после перезагрузки через `/api/auth/me`;
- чат: стартовые подсказки, индикатор ожидания, блокировка повторной отправки,
  отдельный вид технической ошибки с кнопкой «Повторить»;
- состояния ответа `clarify`, `out_of_scope` и нехватка данных показаны как
  нормальное поведение, а не как ошибка;
- источники под ответом в свёрнутом блоке;
- «Новый диалог» с подтверждением и «Завершить диалог»;
- история всех своих диалогов, просмотр только для чтения;
- заявка: предложение, форма, проверка карточки, согласие, создание и номер заявки;
- проверка полей карточки: подсказка по-русски рядом с полем, красная рамка,
  введённое не теряется; отказы backend 422 и 409 раскладываются по тем же полям;
- режим отладки: время ответа, действие, статус ядра, источники, предупреждения;
- экран проверки для сотрудника (`is_staff`): все диалоги и заявки;
- узкий экран телефона, подписи полей, видимый фокус, `aria-live` для новых сообщений.

## Повторы и ошибки

Один `request_id` на отправленное сообщение. Повтор после обрыва сети идёт с тем же
идентификатором: backend вернёт сохранённый ответ и не вызовет модель второй раз.
После ответа 503 сообщение остаётся в истории как `failed`, и повтор отправляется
с новым `request_id` — так описано в `../docs/BACKEND.md`.

## Чего ждём от ролей №1 и №2

- поля расширенной отладки в ответе сообщения: найденные поиском кандидаты,
  фрагменты, переданные модели, и длительность этапов. Сейчас есть только
  `elapsed_ms` и процитированные `sources`; панель отладки покажет остальное
  автоматически, как только поля появятся;
- `preview` в списке диалогов, чтобы не дочитывать каждый диалог ради первой реплики;
- решение по раздаче `frontend/dist` в Docker-образе;
- решение по виджету на стороннем сайте: сейчас CSP содержит `frame-ancestors 'none'`.
