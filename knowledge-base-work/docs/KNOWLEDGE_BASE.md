# База знаний Energytool: подготовка и передача команде

Проверено 12 ноября 2026 года (МСК), на коде `main` версии `2f2be70`.
Работа выполнена в локальной ветке `Аня`. Этот документ описывает подготовку
данных; подключение полноценного консультанта к backend здесь не заявляется.

## Что изучено

- Репозиторий: CSV-baseline `solution.py`, контракт `core_contract.py`,
  исходный `core/`, устройство backend и `docs/CORE_INTEGRATION.md`.
- Технический регламент DOCX и презентация кейса PDF.
- Три переданных плана: решение и архитектура; команда и календарь;
  проверка, демонстрация и сдача. Это планы, а не свидетельства готовности.
- Оба demo CSV, оригинальный список разрешённых зависимостей,
  `sample_submission.zip` и `knowledge-base.zip`.

В пример сабмита просмотрены исходники и README; обращения к API организаторов
не выполнялись. Demo-ответы — примеры поведения, не скрытые эталоны и не источник
продуктовых фактов. В поисковый корпус вошли только документы `knowledge-base.zip`.

## Как воспроизвести подготовку

Требуется Python 3.10+ и стандартная библиотека; установка пакетов не нужна.
Из корня проекта, положив предоставленный архив в `data/knowledge-base.zip`:

```bash
python3 scripts/prepare_knowledge_base.py --archive data/knowledge-base.zip
python3 -m unittest discover -s tests -p 'test_prepare_knowledge_base.py' -v
```

Повторный запуск с тем же архивом сохраняет идентичный результат. Для другой
версии архива укажите новые `--sources` и `--artifacts`: скрипт не перезаписывает
отличающиеся существующие файлы. Исходники и служебные файлы должны находиться
в разных непересекающихся каталогах.

Фрагменты разделены по заголовкам второго уровня. Таблицы, вложенные разделы
и следующие за ними оговорки сохранены целиком. Жёсткого обрезания по числу
символов нет: максимальный фрагмент текущей базы — 4 889 символов. Это не замер
токенов модели и не окончательный выбор параметров поиска.

У фрагмента есть `document_id`, `chunk_id`, `title`, `section`, `source_path`,
`line_start`, `line_end`, `text` и контрольная сумма. `page=null`, потому что
источники Markdown, а не страницы PDF. Дата и версия документа оставлены
неизвестными: упоминание даты закона в тексте не является датой документа.
`related_context_chunk_ids` ссылается на ограничения того же документа;
его должен учитывать будущий слой отбора контекста. Общие справочные разделы
с оговорками также нужно включать по смыслу запроса.

## Проверки и ограничения

- Все 19 исходников побайтно совпадают с архивом; CRC архива корректен.
- Соединение фрагментов каждого документа восстанавливает полный текст.
  Проверены диапазоны строк, уникальность ID и ссылки на связанные фрагменты.
- Восемь тестов подготовки прошли на вымышленных данных: сохранность таблиц
  и оговорок, повторяемость, защита существующих файлов и ошибки входного архива.
- Текущий `solution.py` загрузил все 19 документов и сформировал корректный
  CSV для всех 18 demo ID без обращения к модели. Проверены заголовки, ID,
  непустые ответы и ограничение длины. Продуктовая точность не оценивалась.
- В источниках обнаружены два структурных замечания: отсутствующая внутренняя
  ссылка и экранированный заголовок. Их расположение есть в `manifest.json`.
  Текст не исправлялся, все сведения сохранены в корпусе.

## Передача Даньку и коллеге три

Для локальной проверки существующего baseline передавайте в `DATA_DIR`
именно `data/knowledge-base`, а путь к вопросам задавайте отдельно через
`QUESTIONS_PATH`. Не указывайте общий `data/`: рекурсивный загрузчик может
принять реестр, отчёты и demo CSV за продуктовые источники.

Подготовленные 148 фрагментов пока не используются `solution.py`: его
собственное разбиение по абзацам дало 758 фрагментов. Замена поиска и
разбиения относится к ядру Данька; в этой работе `solution.py` не менялся.
Для коллеги три подготовлен локальный `demo_source_map.jsonl` с подходящими разделами
для проверки, но без утверждения, что текущие ответы уже прошли приёмку.

Для интеграции остаются:

1. На платформе читать `DATA_DIR/knowledge-base.zip` и строить корпус при
   запуске. Нынешний baseline архивы не читает. Скрипт подготовки расположен
   в `scripts/` для локальной работы; это не готовый платформенный импортёр.
2. Использовать текст и условия разделов вместе, проверить поиск на размеченных
   вопросах. Примеры ответов не включать в продуктовый индекс.
3. Подключить общее ядро через фабрику из `docs/CORE_INTEGRATION.md` и проверить
   генерацию с настоящим API. В `Source.excerpt` передавать использованную цитату;
   служебные поля JSONL не добавлять в строгий контракт ответа.
4. В платформенный ZIP включать только необходимые корневые Python-модули
   и `requirements.txt`. Саму базу, готовые индексы и этот локальный пакет
   туда не включать: базу предоставляет платформа.
