## Как подключать данные к новому загрузчику

При запуске из корня репозитория задайте абсолютный путь к
`knowledge-base-work/data` в `DATA_DIR`. Внутри него находится
`knowledge-base.zip`, а рядом — каталог `knowledge-base/`.
Либо укажите в `CORE_KB_PATH` абсолютный путь непосредственно к исходному
архиву или каталогу документов.

Старое указание `DATA_DIR=.../data/knowledge-base` предназначалось для
прежнего baseline. Новый загрузчик без `CORE_KB_PATH` ищет *внутри*
`DATA_DIR` архив `knowledge-base.zip` или каталог `knowledge-base`.

Для Docker `KNOWLEDGE_DIR` указывает на эту родительскую папку `data`,
которая монтируется read-only через `compose.knowledge.yaml`.
При обычной работе нужны `CORE_MODE=real`, `CORE_DEMO=false` и настроенный API.
Чтение базы отдельно от генерации не требует API.

`data/kb-artifacts/chunks.jsonl` — артефакт подготовки и сверки.
Новый загрузчик не использует его как готовый индекс: он читает исходники
и создаёт собственные ID. Не подставляйте каталог артефактов вместо базы.

## Что обнаружено в поиске

По умолчанию новое ядро создало 504 фрагмента из тех же 19 документов.
Проверка использовала его настоящий BM25, обработку истории, `TOP_K=5`,
размер фрагмента 1800 символов и бюджет контекста 14000 символов.
Код ядра в этой работе не изменялся; вызовов модели не было.

Для 24 сценариев с ответом:

- в 19 случаях top-5 включал документ выбранного размеченного основания;
- в 12 случаях контекст включал все выбранные точные основания.

Это **строгая проверка выбранных цитат**, не общая оценка качества ответа.
Восемь из 12 неполных совпадений при разборе оказались случаями с другим
подтверждающим фрагментом. Их нельзя объявлять ошибками модели или поиска
только по несовпадению с первоначальной разметкой.

Подтверждены следующие поводы для доработки ядра Даньком:

1. **27 фрагментов состоят только из оформления Markdown.** У одного
   проверенного запроса такой разделитель занял первое место. Название
   раздела участвует в ранжировании, даже если сам текст — только дефисы.
   Нужна фильтрация таких фрагментов и регрессионный тест на вымышленном
   Markdown, сохраняя настоящие строки таблиц.
2. **KB12, KB15, KB18:** необходимое условие не попало в полный передаваемый
   контекст. Это замечание к отбору источников; фактического ответа LLM
   пока нет. В закрытом отчёте есть вопросы, ожидаемые основания и ID выдачи.
3. **KB21:** контекст даёт лишь частичное основание. Требуется проверить,
   что явная оговорка из источника не теряется при подготовке ответа.

Ручной разбор: `data/review/retrieval_triage.csv`. Полная выдача, параметры,
ID фрагментов и контрольные суммы разметки: `data/review/core-report.json`.
Эти результаты не являются измерением на скрытом наборе платформы.

## Как воспроизвести проверку

Из папки `knowledge-base-work`:

```sh
python3 -m unittest discover -s tests -v
python3 scripts/review_knowledge_base.py
```

Вторая команда по умолчанию читает `data/review/product_facts.csv` и
`data/review/cases.jsonl`; для командной копии добавьте `--review team-review`.
Валидатор подтверждает цитаты и структуру,
но не доказывает логическую правильность пересказа или отсутствие сведений.

Для проверки поиска используйте интерпретатор с зависимостями
`requirements-core.txt` проверяемого ядра:

```sh
python scripts/review_knowledge_base.py \
  --core-root /absolute/path/to/reviewed/project \
  --core-revision REVISION \
  --output data/review/core-report.json
```

Указанный каталог должен содержать `core/` и `core_contract.py` нового ядра.
Он используется только для проверки; изменения рабочей ветки и слияние
не выполняются. Используйте имеющиеся копии проекта; каждая облачная
задача уже изолирована, новый Git worktree без явной просьбы не нужен.
Скрипт не импортирует LLM-клиент и не генерирует ответы.
