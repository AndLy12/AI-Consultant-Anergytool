# Как работают тесты и CI — инструкция для команды

## Главное за минуту

**Тесты — это автоматические проверки программы. CI — это их автоматический запуск после отправки кода на GitHub.**

Пример: вы изменили обработку ответов модели и случайно сломали сохранение файла.
Тест запускает программу на небольшом примере и замечает ошибку. GitHub показывает,
что проверка не прошла, а в журнале можно увидеть причину.

Каждому участнику достаточно знать четыре вещи:

1. Перед отправкой кода желательно запустить тесты у себя.
2. После отправки кода на GitHub проверки запускаются автоматически.
3. Красный результат нужно открыть и разобраться в причине.
4. Зелёный результат означает, что имеющиеся автоматические проверки пройдены.
   Качество ответов настоящей модели оцениваем отдельно.

## Где всё лежит

| Что | Где находится | Для чего нужно |
| --- | --- | --- |
| Скрипт сабмита | `solution.py` в корне проекта | Ранний CSV-baseline; ядро Данька подключается отдельно. |
| Автоматические тесты | Файлы `test_*.py` в папке `tests` | Запускают проверки и сравнивают результат с ожидаемым. |
| Настройка CI скрипта | `.github/workflows/ci.yml` | Проверяет CLI, CSV и обработку ответов модели. |
| Настройка CI backend | `.github/workflows/backend.yml` | Полный набор с веб-зависимостями на SQLite/PostgreSQL. |
| Сценарии проверки ответов | [QUALITY_CASES.md](QUALITY_CASES.md) | Вопросы к настоящей модели и критерии оценки её ответов. |

**Отдельно загружать папку тестов в GitHub Actions не нужно.**
И программа, и тесты, и настройка CI хранятся в одном репозитории.
GitHub получает их вместе. Файл `.github/workflows/ci.yml` тоже должен быть
добавлен в коммит и отправлен на GitHub.

## Что происходит после отправки кода

1. Участник отправляет изменения на GitHub — это называется **push**.
2. GitHub запускает наш сценарий проверок **Project checks**.
3. На отдельном компьютере GitHub скачивает проект, подготавливает Python и устанавливает зависимости.
4. Проверяет скрипт на Python 3.10 и 3.12. Отдельный workflow backend проверяет
   полный проект с веб-зависимостями на Python 3.12 и двух СУБД.
5. Показывает результат: успешно или с ошибкой.

Проверки также запускаются при создании или обновлении **pull request** —
предложения добавить изменения из своей ветки в общую. Поэтому одна отправка
может вызвать два запуска: по push и по pull request. Это ожидаемо.

Наш CI только проверяет проект. Он не обновляет сайт и не отправляет решение
на платформу соревнования.

## Как запустить тесты у себя

Откройте терминал в корне проекта — в папке, где находится `solution.py`.
На Mac выполните:

```bash
source .venv/bin/activate
python -m pip install -r requirements-web.txt
python -m unittest discover -s tests -v
```

Эта команда означает: «найди автоматические тесты в папке `tests`, запусти их
и покажи результат каждой проверки». Ничего менять в команде не нужно.
Если в вашем окружении Python запускается командой `python`, используйте её вместо `python3`.
Для полного проекта требуется Python 3.12 или новее. Скрипт solution.py
отдельно проверяется на Python 3.10 и 3.12; точную версию платформы сверяет Данёк.

Для текущих тестов не нужны ключ API или платные запросы. Полный набор требует
веб-зависимости; CLI/CSV-проверки используют стандартную библиотеку Python.
Тестовые файлы создаются во временных папках и затем удаляются.

### Как читать результат

| Надпись | Что означает | Что делать |
| --- | --- | --- |
| `ok` | Одна проверка прошла. | Читать дальше до общего результата. |
| `OK` в самом конце | Все запущенные проверки прошли. | Можно отправлять изменения на проверку команды. |
| `FAIL` | Программа выдала результат, который не соответствует ожиданию теста. | Посмотреть название проверки, ожидаемое и фактическое значение. |
| `ERROR` | Во время проверки возникла ошибка. | Прочитать сообщение и строки с местом ошибки. |
| `FAILED (...)` в конце | Есть неуспешные проверки. | Исправить причину и повторить запуск. |

Количество проверок может изменяться по мере развития проекта.
Некоторые проверки перебирают несколько вариантов данных внутри одного теста.

## Где посмотреть результат на GitHub

1. Откройте репозиторий проекта.
2. Перейдите во вкладку **Actions**.
3. Выберите **Project checks**, затем запуск для вашей ветки и отправленных изменений.
4. Откройте задание **Tests (Python 3.10)** или **Tests (Python 3.12)**.
5. Если есть ошибка, откройте неуспешный шаг. Ошибки тестов будут в шаге
   **Run unit, integration and CLI acceptance tests**.

Если запуск ещё идёт, дождитесь завершения. Если он отменён из-за новой отправки
в ту же ветку, смотрите более новый запуск.

Для ручного повторного запуска можно использовать **Re-run jobs** у завершённого запуска.
Для нового ручного запуска предусмотрен **Run workflow** на странице сценария,
когда файл настройки уже есть в основной ветке и у вас достаточно прав.

Новый запуск Project checks проверяем после отправки этих изменений.
Backend CI уже запускался успешно; локальная проверка не заменяет проверку CI.

## Что делать, если проверка красная

1. Откройте неуспешный шаг и найдите причину.
2. Если упал тест, запустите всю команду тестов у себя.
3. Исправьте проблему и повторите локальную проверку.
4. Отправьте исправление в ту же ветку — GitHub проверит его автоматически.

Если тесты даже не начались, посмотрите предыдущие шаги: проблема может быть
в установке зависимостей или настройке окружения. При сбое сервиса GitHub иногда
достаточно повторить запуск; ошибка приложения требует исправления.

**Не удаляйте проверку и не ослабляйте ожидаемый результат только ради зелёной галочки.**
Если команда осознанно изменила поведение программы, обновите тест под новое
согласованное поведение. Если непонятно, что сломалось, передайте ответственному
ссылку на запуск, название проверки и текст ошибки.

Красный CI сам по себе не запрещает объединение веток. Чтобы GitHub запрещал
слияние при ошибках, владелец репозитория должен отдельно настроить обязательные
проверки в правилах защиты общей ветки.

## Что именно проверяется сейчас

| Файл | Что проверяет простыми словами |
| --- | --- |
| `test_solution.py` | Пять исходных проверок: работа с вопросами, поиском, настройками и CSV. |
| `test_acceptance.py` | 11 проверок запуска программы отдельным процессом: чтение входного файла, настройки, ошибки, повторный запуск и итоговый CSV. |
| `test_http_integration.py` | 9 проверок совместной работы частей приложения: подготовка запроса к модели, передача истории и базы знаний, обработка ответа и сохранение результата. |
| `test_backend.py` | Аккаунты, история, права, заявки и миграции БД. |
| `test_core_connection.py`, `test_async_core.py` | Подключение ядра Данька, проверка контракта, async-история и таймаут. |

В частности, проверяем, что:

- идентификаторы вопросов не теряются, а `001` не превращается в `1`;
- файл результата содержит колонки `id,answer`, непустые ответы и допустимую длину;
- кириллица, кавычки и переносы строк корректно сохраняются;
- неверный входной файл приводит к понятной ошибке;
- пустой вопрос или отсутствие информации обрабатываются предусмотренным способом;
- в запрос к модели попадают вопрос, история и найденная информация;
- ошибки API, слишком долгое ожидание и некорректный ответ не обрывают всю обработку;
- после временного сбоя выполняется предусмотренное количество повторных попыток.

### Почему в тестах нет настоящей модели

Вместо сетевого обращения тест подставляет заранее подготовленный ответ или ошибку.
Это называется **заглушка**. Остальные части приложения выполняются по-настоящему.
Так можно быстро и повторяемо проверить успешный ответ, отказ API и тайм-аут,
не расходуя деньги и не завися от доступности модели. Паузы между повторами
отключаются только на время этих тестов.

Поэтому тест с заглушкой подтверждает правильность обработки ответа,
но не доступность настоящего API, работу реального сетевого соединения
или правильность рассуждений модели.

## Что нужно проверить отдельно

**Зелёный CI не гарантирует, что консультант правильно ответит на любой вопрос.**

В [QUALITY_CASES.md](QUALITY_CASES.md) есть 14 сценариев для настоящей модели:
правильность фактов, уточняющие вопросы, использование истории, отсутствие
выдуманных цен и выполнение правил. Их нужно прогонять отдельно и записывать
результат. Сейчас это список для оценки, а не автоматически пройденные проверки.

API backend уже проверяется автоматически, а веб-интерфейс проверялся браузерным
прогоном отдельно. Автоматические браузерные проверки, Docker и нагрузка в CI
пока не включены. Ручной список интерфейса находится в `QUALITY_CASES.md`.

## Если вы меняете программу

Запускайте проверки перед отправкой кода. Если добавляете новое важное поведение,
добавляйте проверку для него. Если меняется расположение файлов, способ запуска
или формат результата, согласуйте это с командой: потребуется обновить связанные тесты.

Обычному участнику не нужно редактировать `ci.yml` при каждом изменении программы.
Новый test_*.py в папке tests автоматически попадёт в полный backend CI.
Для независимого CSV-скрипта список трёх файлов в ci.yml задан явно: новые
платформенные тесты нужно добавить туда, не подключая веб-зависимости.
